# 系统资源调配（R 轮，2026-11-11）

> 本轮主题：**在不改变任何用户可见功能的前提下**，把 CPU、时钟节拍、内存布局
> 三类资源的调配从「隐式、脆弱、靠运气」改成「显式、可预算、可量化」。
> 全文数据均来自可复现脚本，见文末「验收清单」。

---

## 一、起点：一次实测暴露的架构问题

用 `test_idle_cpu.py`（宿主侧读 `/proc/<qemu-pid>/task/*/stat` 的 utime+stime
jiffies，guest 无法伪造）测「图形桌面静置 8 秒」的 CPU 消耗：

```
r0_busy: CPU=4.00 s / wall=8.00 s = 50.0%
```

不是 100%，而是 **50%** —— 这个数字本身解释了老架构：

- 全局 timer 只有 10Hz，`handle_irq` 每次 TIMER IRQ 都 `task_switch()`，
  在 task0(内核/桌面) 与 task1(worker) 之间严格轮转，各占 100ms 时间片；
- P3 之后桌面主循环是 `yield` **忙等**（为了输入即时，去掉了 `wfi`），
  于是 task0 的那 100ms 片烧满 CPU；
- task1 的 100ms 片里立刻 `wfi` 睡觉，几乎不耗 CPU；
- 平均下来正好一半。

P3 解决了「输入排队 100ms」，代价是**空闲占满一整核**。二者看似不可兼得：
`wfi` 只能被 IRQ 唤醒，而整机只使能 UART(33) 与 TIMER(30)，xHCI 是纯轮询设备
没有 IRQ —— 一旦睡，就退回 100ms 延迟。这正是 P3 当初必须去掉 `wfi` 的原因。

## 二、CPU 与时钟：硬件唤醒频率 与 软件 tick 解耦

### 2.1 约束：`tick` 不能提频

`tick` 被写死成 **10Hz**（`1 tick = 100ms`），消费者遍布全内核：

| 位置 | 用途 |
| --- | --- |
| `fs.c` (7 处) | `mtime = tick / 10` |
| `kernel.c` | EL0 看门狗 `EL0_TIMEOUT_TICKS 300` = 30 秒 |
| `kernel.c` | task1 心跳、抢占轮转 `task_switch()` |
| `desktop.c` | 时钟 `fmt_time(tick/10)`、秒更新、安装向导 10 秒超时 |
| `net.c` / `tcp.c` | DHCP xid、TCP TIME_WAIT 超时 |

### 2.2 设计：cycle 结算，不数 IRQ

`timer_set_wake_hz(hz)` 让硬件 timer 独立跑 120~1000Hz，只负责把 CPU 从 `wfi`
叫醒去 `usb_kbd_poll()`；`tick` 则由 `cntpct_el0` 的**真实经过 cycle** 结算：

```c
g_tick_cyc_acc += cyc - g_tick_last_cyc;
g_tick_last_cyc = cyc;
while (g_tick_cyc_acc >= g_tick_period) {   /* g_tick_period = freq/10 */
    g_tick_cyc_acc -= g_tick_period;
    tick++;
    /* ...EL0 看门狗、抢占轮转（仅非桌面态）... */
}
```

一次 IRQ 间隔若跨过多个 10Hz 周期（低频唤醒 / 调度延迟）会**补多个 tick，绝不丢拍**。
串口 shell 下 timer 本就 10Hz、每 IRQ 恰好一个周期，与原版「每次 IRQ tick++」逐字节等价
（`test_behavior.py --compare golden_behavior.txt` 逐字一致验证）。

> **踩坑 1：不能用「每 N 次 IRQ 才 tick++」分频。** QEMU TCG 下
> `cntp_tval_el0` 按 `freq/hz` 设定后，实际 IRQ 触发率并不精确等于 hz
> （实测设 1000Hz 只触发 ~558Hz）。数 IRQ 会让 tick 漂移到 6.67Hz，
> 把 fs mtime、看门狗、桌面时钟全部带偏。改为 cycle 结算后实测 3.2s 精确 +32 tick。

### 2.3 桌面态抑制抢占轮转

`g_desktop_active=1` 时 `handle_irq` 不做 `task_switch()`。原因：GUI 主循环跑在
task0，若 `wfi` 醒来被切到 task1，桌面要等下个 10Hz 边界才切回 → 优化会被 100ms
抢占卡死。桌面期间让 GUI 独占 CPU0，**退出桌面自动恢复轮转**（串口 shell 语义零变化）。

### 2.4 自适应调频 + 事件驱动休眠

| 空闲时长 | 档位 | 唤醒频率 |
| --- | --- | --- |
| 刚有输入 <200ms | ACTIVE | 1000 Hz |
| 200ms~2s | IDLE | 250 Hz |
| ≥2s | DEEP | 120 Hz（仍满足 60fps 闪烁 + 10Hz tick） |

- **有输入时全速不睡**：`real_input` 为真则不 `wfi`，连续轮询 —— P3 的跟手感原样保留；
- **无输入时 `wfi`**：被高频 IRQ / UART IRQ 唤醒即回循环顶部 harvest；
- 任意输入立刻回 ACTIVE 档。

> **踩坑 2：空闲计时不能用 `cntpct_el0`。** QEMU TCG 的虚拟计数器与墙钟不一致，
> `idle_ms` 被严重低估，降档判据永远算不到阈值（实测卡在 250Hz）。
> 改用 `tick`（已证明恒 10Hz、与真实时间同步）计时：`idle_ticks = tick - last_input_tick`。
>
> **踩坑 3：空闲起点只认真实键鼠事件。** 主循环里闪烁光标 / 时钟秒更新 /
> 安装超时都会把 `input` 置 1；若用 `input` 刷新 `last_input_tick`，会被每 500ms
> 的闪烁不断刷新 → 永远降不到 DEEP 档。独立出 `real_input`（仅键盘 ring / 鼠标事件置位）。

### 2.5 结果

```
忙等版(P3)       50.0%   CPU=4.00s / 8s
首版 wfi          1.9%   CPU=0.15s / 8s
最终(DEEP 档)     0.6%   CPU=0.05s / 8s     ≈ 83 倍
```

`test_resource_live.py` 用 QMP 直接读 guest 内存里的统计量，**证明省电不是靠冻住画面**：
TIMER IRQ 与 wfi 命中持续增长、桌面态=1、自适应降到 120Hz、tick 恒 10Hz —— ALL PASS。

## 三、内存：DMA 缓冲的段归属守卫 + 「真实画面」判据

> 本节含一次**重要自我勘误**：本轮曾尝试「把 DMA 缓冲钉到固定物理地址」，
> 7 组实验一度判定可行，最终被全套图形回归推翻。过程完整记录，避免后人重踩。

### 3.1 起点：上一轮（P3）的结论

P3 曾把图形启动挂死（日志止于 `[probe] A pl011 ok`）归因为
「fw_cfg DMA 缓冲必须留在 `.data`」，并加了「段类型必须 d/D」的守卫。
本轮先想进一步把地址**钉死**，彻底解耦浮动段链。

### 3.2 第一版实验链（判据有误，结论作废）

| 实验 | 做法 | 当时的结论 |
| --- | --- | --- |
| V0/V1 | `.rodata` +128B | V1 稳定 4/4 挂在 `[probe] A`，V0 稳定 2/2 进桌面 |
| 逐笔插桩 | `fwc_dma_write` 每次 MMIO 打点 | 插桩版（地址也变了）反而完整进桌面 |
| padding 扫描 | `.data` 内加 0~384B | 缓冲地址**全都不变** |
| `.data` 钉死 | 起点钉在 0x400AE3F0 / +0x110 | D1（缓冲 0x400ae590）进桌面；D2/D3 被空间守卫拦下 |
| 密集地址扫描 | `.rodata` +16~384B 逐档 | 「危险窗口」`0x400ae4f0/500/510` 挂死，其它地址进桌面 |
| 逐符号 ELF 对比 | YES(D1) vs HANG(n128) | `.bss`/栈/`.nvmedma`/段边界完全相同，唯一差异 = 缓冲绝对地址 |
| 固定物理地址 | 缓冲钉到 `0x4007E000` | **进桌面成功**，+2KB/+6KB 扰动下仍「正常」 |

据此一度得出「地址敏感 → 钉死即可根治」，把缓冲改成绝对地址宏
`FWC_CFG_BUF/FWC_DMA_DESC`，并重写 `build.sh` 守卫。

### 3.3 致命误区：串口「假绿」

上面 7 组实验全部用「串口出现 `图形桌面已就绪` / `fwcfg ramfb 已配置`」当成功判据。
**这两句都是内核无条件打印的**——QEMU 的 fw_cfg DMA 可能压根没建立 ramfb
display surface。全套图形回归随即打脸：P2 桌面 / P2.1 校准 / P2.2 跟随的画面
差异**全部 0.000**，`colors=2`（纯黑），而串口日志、CPU、wfi/tick/调频计数全正常。

用**真实画面**重做 A/B（QMP `screendump` 直接看像素）：

| 缓冲方案 | screendump | 判定 |
| --- | --- | --- |
| 静态数组 `.data`（HEAD `0x400ae480`） | 800×600，97 色，中心 `(8,12,20)` | ✅ 真桌面 |
| 静态数组 `.data`（`0x400b8778`，P3 前） | 800×600 彩色 | ✅ 真桌面 |
| 固定地址 `0x4007E000`（`< 0x40080000`） | **640×480 纯黑** | ❌ surface 未建 |
| 固定地址 `0x400ae480/520/7F000`（各种） | 640×480 纯黑 | ❌ 同样黑屏 |

真因：fw_cfg DMA 缓冲必须是**内核镜像 LOAD 段内的真实 RAM**（PROGBITS，
`={1}` 让链接器写入初值、QEMU 加载器把该页纳入镜像）。改成绝对地址宏后，
那块地址不被任何 LOAD 段覆盖，descriptor 读出来无效 → ramfb surface 没建立 → 黑屏。
`0x40000000-0x4007FFFF` 更是 QEMU loader/DTB 暂存区，绝不能放 DMA 缓冲。
扫描出的「危险窗口」是「挂死」判据下的现象，但**即使不挂死也可能是静默黑屏**——
用错了判据，整个方向越走越偏。

### 3.4 最终方案（磁盘真实版本）

回退到静态数组，**不引入新段/宏**，用「行为测试兜底」替代脆弱的地址约定：

```c
static u8 fwc_cfg_buf[28] __attribute__((aligned(8))) = {1};
static u8 fwc_dma_desc[16] __attribute__((aligned(8))) = {1};
```

- `={1}` 落 `.data`（PROGBITS），与 `.bss` 中段插入变量的地址漂移解耦（P3.2 事故）；
- `build.sh` 守卫校验两符号段类型 `d/D` 且 `nm` 绝对地址 **≥ `0x40080000`**
  （内核镜像加载区内、QEMU 已映射的普通 RAM；禁止退回 `.bss` 或改绝对地址宏）；
- 新增 **`test_framebuffer.py`**：每次回归直接对 screendump 做像素级判定
  —— 尺寸必须 `800×600`（surface 建成才是这个尺寸，没建成 QEMU 回退 640×480）、
  颜色数 >16、非背景占比 >1%。任一不满足即 FAIL 并明确打印「黑屏/未建 surface」，
  **杜绝「串口一切正常但屏幕全黑」再次静默假绿**；
- `diag_res.py`：图形链路异常时读 guest 计数，判定「wfi 是真省电还是睡死」。

结论修正为：`.rodata/.data` 浮动布局确实会让缓冲地址随新增代码漂移，
但**根治手段不是钉地址，而是用真实画面判据在每次回归里守住**——
只要加代码后画面仍出，DMA 就正常；一旦黑屏/HANG，`test_framebuffer.py` 立刻 fail fast。
这比「固定地址 + 一堆段/对齐约定」稳健得多（后者反而因脱离 LOAD 段必然黑屏）。

## 四、可观测性

### `res` 命令（串口 / 图形终端都可敲）

```
[res ] ==== 系统资源账 ====
[res ] 软件 tick(10Hz)=4  硬件唤醒=10Hz  分频=1  桌面态=0
[res ] TIMER IRQ 累计=4  桌面 wfi 命中=0  (wfi/IRQ 越高=空闲越省 CPU)
[res ] 内核上界余量=4096 B  .nvmedma_end=...  USER_BASE=...
[res ] SMP 在线: cpu0=Y cpu1=N cpu2=N cpu3=N  本核 tick=1
```

刻意**不写进 `help` 文本、不进 `golden_behavior.txt` 的 29 条命令集** ——
这两处是逐字比对的基线，加一行就会误报回归。

### 三个验证脚本

| 脚本 | 手段 | 验证什么 |
| --- | --- | --- |
| `test_idle_cpu.py` | 宿主 `/proc` jiffies | 桌面空闲 CPU 占用（guest 无法伪造） |
| `test_resource_live.py` | QMP `xp` 读 guest 内存 | wfi/IRQ 持续增长、自适应档位、tick 恒 10Hz、桌面态 |
| `test_behavior.py --compare` | 串口启动日志 + 29 命令逐字 diff | 用户可见功能零变化 |

## 五、诚实的边界

- CPU 数字来自 **QEMU TCG 沙箱**。真机 KVM 下 `wfi`/timer 语义更接近硬件，
  降幅方向一致但绝对值不同；装机后建议用 `res` 复核一次。
- **xHCI 仍是纯轮询**（未加 MSI 中断驱动）。高频唤醒 IRQ 是为「纯轮询设备要低延迟
  又要能睡眠」付出的固定小成本；DEEP 档已把这笔成本压到 120Hz。
- 本轮**未做**内存池 / 动态分配 / SMP 主逻辑分工 / USER_BASE 扩容。
  静态预算模型不变，上界余量仍是 4KB（有分段预算守卫与扩容指引）。
  DMA 缓冲保持 `.data` 静态数组、地址随段链浮动这一点**没有从布局上根治**，
  而是靠 `test_framebuffer.py` 的真实画面判据在每次回归里守住——
  这是行为兜底，不是结构消除；真正要根治按
  [内核空间预算与扩容指引](内核空间预算与扩容指引.md)第六节走。
- 桌面态抑制抢占轮转期间，task1 心跳在 GUI 期间不打印；退出桌面即恢复，
  串口 shell 路径完全不受影响（行为基线逐字一致）。
- **方法论教训（本轮最大收获）**：图形内核的「成功」必须用 **screendump 真实像素**
  判定，绝不能用「串口日志出现某句话」——后者可能全绿而屏幕纯黑。7 组实验的方向性
  错误根源就在这里，已固化成 `test_framebuffer.py` 纳入每次回归。
