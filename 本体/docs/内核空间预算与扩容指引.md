# 内核空间预算与扩容指引

> 2026-11-10 · ARM 内核结构性优化（阶段三）产出
>
> 一句话：**`USER_BASE` 之前的每一页都要算账**。本文给出当前链接布局、上界余量
> 为什么会 ±4 KB 跳变、每次构建自动打印的预算守卫，以及后续新功能真需要更多
> 空间时该怎么扩。涉及的所有地址均来自 `kernel.elf` 的 `nm` / `objdump` 实测。

## 一、为什么需要这份文档

LoongOS 没有堆分配器，窗口、图形缓冲、页表、virtio/NVMe 队列、32 KB 内核栈全是
静态数组，链接期就固定在 `USER_BASE` 以下的内核镜像里。历史上踩过一次极隐蔽的
故障：`.bss` 涨过 `USER_BASE` 后**编译零警告、开机正常**，但 `run` 用户程序会踩进
内核数据区，静默全废。因此 `build.sh` 很早就加了 BSS 守卫（读真实 `__bss_end` 与
`__nvmedma_end`，越界即 fail fast）。

2026-11-10 的块设备抽象层（`blkdev`）又暴露出第二层问题：内核上界余量会在
**±4 KB 之间跳变**，而「构建成功 / 四项检查通过」完全看不出来。于是把守卫从
「越界才报错」升级成「每次构建都把空间账打印出来，并与上一次对比」，本文即这套
机制的设计说明与后续扩容手册。

## 二、当前链接布局（阶段二后 `kernel.elf` 实测）

| 段 | 起始 VMA | 大小 | 用途 |
| --- | --- | --- | --- |
| `.text` | `0x40080000` | 120.3 KB (`0x1e10c`) | 内核代码，`.text.boot` 在最前 |
| `.el0text` | `0x4009f000` | 4 KB | EL0 演示代码独占页，页表单独标权限 |
| `.rodata` | `0x400a0000` | 57.0 KB (`0xe3e4`) | 只读数据 |
| `.data` | `0x400ae3f0` | 30.0 KB (`0x77f8`) | 可写数据（含 `blk_drivers` / `*_ops` 表） |
| `.got` / `.got.plt` | `0x400b5be8` | 296 B | 编译器生成的 orphan 段 |
| `.bss` | `0x400b6000` | 1353.4 KB (`0x1525c0`) | 页表 / 设备队列 / 窗口缓冲 + **32 KB 内核栈** |
| `.nvmedma` | `0x40209000` | 24 KB (`0x6000`) | 6×4 KB NVMe DMA 页，**内核真正上界** |
| `USER_BASE` | `0x40210000` | — | 用户程序区起点 |
| `USER_END` | `0x40400000` | — | 用户程序区终点 |

关键边界符号：

```
__bss_end        = 0x402085c0     # .bss 真实终点（含栈）
__nvmedma_start  = 0x40209000     # ALIGN(4096) 后的 DMA 区起点
__nvmedma_end    = 0x4020f000     # 内核真正上界
DMA 对齐浪费      = 2624 B        # __nvmedma_start - __bss_end
上界余量 margin   = USER_BASE - __nvmedma_end = 4096 B  (4.0 KB)
```

优化前（`v1.1.2` / md5 `072bbda9…`）对应 `__bss_end=0x402075c0`、
`__nvmedma_end=0x4020e000`、余量 **8 KB**。

> 注意：**内核上界不是 `__bss_end`，而是 `__nvmedma_end`**。`.nvmedma` 排在 `.bss`
> 与内核栈之后，且整体 `ALIGN(4096)`；只看 `__bss_end` 会漏掉这 24 KB。

## 三、余量为什么会 ±4 KB 跳变（精确根因）

阶段二把 `kernel.elf` 从 `072bbda9…` 改到 `bcb6e939…`，`.data` 只增加了 264 B
（`blk_active` 4 + `blk_init_rc` 32 + `blk_drivers` 32 + 三张 `*_ops` 各 56），
但余量少了整整 4 KB。逐符号比对两份 ELF 的 `.bss` 后定位如下：

```
优化前:  ... l_ring @0x401e2000 (size 0x2000, 终点 0x401e4000)
         0x401e4000  vs_desc        ← 4KB 对齐缓冲，正好落在边界，无填充
         0x401e5000  vs_used
         ...
         0x401fa000  rng_ok
         0x401fc000  g_mmio
         vs_ok 藏在 0x401e6124（vs_avail 之后的对齐空隙里）

阶段二:  ... l_ring @0x401e2000 (终点 0x401e4000)
         0x401e4000  vs_ok (4 B)   ← 这个 4B 标志被重排到了边界槽
         0x401e5000  vs_desc       ← 被迫 4096 对齐到下一页，凭空多 4092 B 填充
         0x401e6000  vs_used
         ...
         0x401fb000  rng_ok
         0x401fd000  g_mmio
```

- `.bss` 内有一长串 `__attribute__((aligned(4096)))` 的设备缓冲（页表、
  virtio 队列、NVMe/网卡缓冲），每个独占一页，按链接顺序线性排布。
- 优化前 `l_ring` 恰好结束在 `0x401e4000`，`vs_desc` 紧接其后、天然对齐，零填充。
- 阶段二统一头文件 / 重构 `virtio_blk.c` / 给 `virtio_scsi.c` 加 `vs_ops` 后，
  编译器重排了 `.bss` 输入段内的符号，`vs_ok` 这个 4 B 标志被挪到组首，占了
  `0x401e4000` 这个边界槽；`vs_desc` 只能退到 `0x401e5000`。
- 于是 **从 `vs_desc` 到末尾 `g_mmio` 的整条 4 KB 对齐链整体后移一页**，
  `_stack_bottom` / `__bss_end` / `__nvmedma_start` / `__nvmedma_end` 全部 +0x1000，
  余量 8 KB → 4 KB。

**两个重要结论：**

1. 这 4 KB **不是空间泄漏，也不是新增 `.data` 挤占**：`.bss_start` 两份都是
   `0x400b6000` 未变，纯属 `.bss` 内部「对齐碎片」对符号顺序敏感。任何源码改动
   都可能让它 ±4 KB 摆动，属于链接器布局的正常现象。
2. **4 KB 余量仍是正值、被硬守卫覆盖、对功能零影响**。它没有越过 `USER_BASE`，
   用户程序区不会被踩穿；行为黄金基线逐字一致，全套回归全绿（见第二十九轮记录）。

因此阶段三**没有**为了「把数字拉回 8 KB」去改链接布局或削减内核栈——那类改动
风险大于收益，且与「功能不变」的保守基调相悖。真正的修复是让这件事**再也不会
悄悄发生**：把余量量化到每一次构建。

## 四、预算守卫（`build.sh`，每次构建自动执行）

### 4.1 分段预算表

构建末尾从 `kernel.elf` 读 10 个链接器符号（`.text/.rodata/.data/.bss/.nvmedma`
各自的 start/end），打印：

```
[budget] ===== 内核空间预算（阶段三 / 每次构建量化）=====
[budget]   .text           120.3 KB  (0x1e10c)
[budget]   .rodata          57.0 KB  (0xe3e4)
[budget]   .data            30.0 KB  (0x77f8)
[budget]   .bss           1353.4 KB  (0x1525c0)  含 32KB 内核栈
[budget]   .nvmedma         24.0 KB  (0x6000)  6x4KB DMA 页
[budget]   DMA 对齐浪费    2.6 KB  (__bss_end -> .nvmedma_start)
[budget]   内核上界 = 0x4020f000   USER_BASE = 0x40210000
[budget] * 上界余量 = 4.0 KB (4096 B)  关注 WARN：新增功能请评估 .bss 对齐碎片
[budget]   阈值: >=6KB 充裕 / [4,6)KB 关注 / (0,4)KB 偏紧 / <=0 禁止构建
[guard] OK 四项检查通过
[budget] 相对 bss_budget.txt 基线：余量 +0 B
```

「DMA 对齐浪费」一项专为本第三节的现象而设：它把 `__bss_end` 到
`.nvmedma_start` 之间的页对齐空隙显式打出来，余量一跳变就能看出是碎片还是真增长。

### 4.2 三级阈值

| 余量 | 等级 | 含义 |
| --- | --- | --- |
| ≥ 6 KB | 充裕 OK | 正常 |
| 4 ~ 6 KB | 关注 WARN | 进入对齐碎片敏感区，新增功能要评估 `.bss` 布局 |
| 0 ~ 4 KB | 偏紧 WARN | 建议按第六节扩容 |
| ≤ 0 | **禁止构建** | 硬检查 fail fast（沿用历史四项守卫） |

软阈值只告警不拦截；四项硬检查（`__bss_end`/`__nvmedma_end` 不得越过
`USER_BASE`、`-Ttext` 必须在 `[USER_BASE, USER_END)`、`.nvmedma` 不得早于
`.bss`）语义保持不变，越界一律 `exit 1`。

### 4.3 团队共享基线 `bss_budget.txt`

每次成功构建把预算写入 `本体/bss_budget.txt` 并纳入版本库：

```
margin_bytes=4096
kernel_upper=0x4020f000
user_base=0x40210000
bss_bytes=1385920
data_bytes=30712
nvmedma_bytes=24576
align_gap_bytes=2624
```

下次构建读入该文件并打印 `相对 bss_budget.txt 基线：余量 ±N B`。这样即便只是
改了个头文件导致符号重排、余量掉 4 KB，也会在构建输出里立刻现形，而不是等到
某天突然越界才发现。构建失败时 awk 在写基线前就 `exit 1`，不会用越界数据污染基线。

> 实现坑（已修）：awk 脚本里曾用 `RS` 当 `__rodata_start` 的变量名，**覆盖了 awk
> 内置的记录分隔符 `RS`**，导致 `getline < bf` 把整个基线文件当成一条记录，
> `^margin_bytes=` 匹配不上、delta 静默丢失。现改为 `ROS/ROE`，并在代码里留了
> 注释防止后人再踩。

### 4.4 越界拦截实证

在临时副本里给 `blkdev.c` 追加一个 20 KB 未初始化静态数组（模拟后续新功能），
构建结果：

```
[budget]   .bss           1373.4 KB  (0x1575c0)
[budget]   内核上界 = 0x40214000   USER_BASE = 0x40210000
[budget] * 上界余量 = -16.0 KB (-16384 B)  越界 FAIL
X __nvmedma_end 已顶到/越过 USER_BASE：NVMe DMA 区会踩穿用户程序区
build rc=1
```

预算表准确反映了 +20 KB 增长，守卫在链接阶段就 fail fast——这是「新增功能
不越界」这条承诺的硬证据，而不只是一句口号。

### 4.5 另一类布局漂移：启动期 fw_cfg DMA 缓冲的段归属守卫（P3，2026-11-10）

余量守卫管的是「空间够不够」，但本轮 P3 踩到的是**另一类**问题：空间明明够、
四项检查全过，图形启动却直接挂死。根因是往 `.bss` 中段插入 136 B 按钮队列变量，
把 `fwc_cfg_buf`/`fwc_dma_desc` 两个静态缓冲从 `0x400b8778/0x400b8798` 推到
`0x400b8808/0x400b8828`，而 QEMU fw_cfg DMA 对描述符/数据缓冲的**绝对地址敏感**
（第四笔 `fwcfg.dma` 触发后 guest 挂住，日志止于 `[probe] A pl011 ok`）。
二分 + 逐笔 MMIO 插桩实证：E1（改 DMA 触发逻辑）仍挂、E2（把缓冲放 `.data`）恢复。

修复是把两个缓冲 `= {1}` 显式初始化落 `.data`，地址与 `.bss` 增长解耦；并在
`build.sh` 加**段归属守卫**：这两个符号的 nm 类型必须 `d/D`（.data）或 `r/R`
（.rodata），落回 `b/B`（.bss）立即 fail fast。正反映证：修复版放行、改回
`.bss` 的副本被拦（rc=1）。

> 教训：静态缓冲的「地址稳定性」和「空间余量」是两回事。凡是参与**设备 DMA /
> 早期启动**的缓冲，要么放进独立固定段（本指引方案 1），要么固定在 `.data`
> 并用段归属守卫钉死，不能让它随 `.bss` 里其它变量的增减而漂移。

## 五、新增功能的检查清单

每次加驱动 / 命令 / 窗口后：

1. `sh build.sh`，看 `[budget] * 上界余量` 与 `相对基线 ±N B`；
2. 新增了 `.c` 就登记进 `build.sh` 的 `KERN_SRCS`（未登记源文件守卫会拦下）；
3. 新增块设备驱动只需导出 `xxx_ops`、在 `blk_drivers[]` 加一项、登记 `.c`，
   **不用改 `kernel.c` 或任何既有驱动**（见 `blkdev.h` 设计说明）；
4. `python3 test_behavior.py --compare golden_behavior.txt` 必须逐字一致；
5. 跑全套回归（见第二十九轮记录）；P3 起桌面手感另有 `test_desktop_p3.py`
   与 X86 的 `test_x86_blink.py`；
6. 若往 `.bss` / `.data` 加了静态变量，图形拓扑要实跑一次「进桌面」——
   `build.sh` 的 fw_cfg DMA 段归属守卫会拦缓冲回落 `.bss`，但地址漂移导致
   的其它设备 DMA 敏感仍需实测覆盖（见 4.5）；
7. 若余量进入「偏紧」或 delta 连续为负，按第六节扩容，不要靠削减内核栈硬凑。

## 六、后续真要更多空间时的扩容路径

按「治本程度」排序，**推荐 1，必要时再评估 2，不做 3**：

### 方案 1（推荐，治本，已于第三十三轮正式采用）：把 4 KB 对齐缓冲收进独立段

> **状态（2026-11-11，第三十三轮）**：本方案已从「未来路径」变为「已落地」。
> 关机/重启功能加了 PSCI 调用 + 4 条命令 + 桌面按钮，净增约 344 字节，
> 把原本就只剩 4 KB 下限余量的内核顶过一页（守卫拦截 rc=1）。按本方案把
> 页表 / virtio 队列 / EL0 演示页等约 30 个 `aligned(4096)` 缓冲收进 `.bss.align4k`
> 后，`align_gap_bytes` 从 **2592 → 0**，余量回到 4 KB，构建通过且行为零变化。

给所有 `aligned(4096)` 的设备缓冲加
`__attribute__((section(".bss.align4k")))`，在 `linker.ld` 里：

```ld
.bss : ALIGN(16) {
    __bss_start = .;
    *(.bss .bss.*)          /* 普通小变量紧凑排列 */
    *(COMMON)
    . = ALIGN(4096);
    *(.bss.align4k)         /* 4KB 对齐缓冲统一放这里，内部顺序不再影响小变量 */
    . = ALIGN(16);
    _stack_bottom = .;
    . += 32 * 1024;
    _stack_top = .;
    __bss_end = .;
} :data
```

- **优点**：彻底消除第三节的 ±4 KB 敏感性；小变量再怎么重排都不会把整条
  对齐链顶后一页；余量可预期。
- **代价**：要给约 30 个数组加 section 属性，改 `linker.ld`，且必须重跑全套
  回归 + 用行为黄金基线确认零行为变化。属于「下一次专门做内存布局重构」时的事，
  不适合夹在本次功能不变的优化里顺手做。

### 方案 2（空间最大，连锁改动多）：上移 `USER_BASE`

把 `USER_BASE` 从 `0x40210000` 上移（例如 `0x40220000`），给内核多留 64 KB。
**必须同步**：`kernel.c` 的 `USER_BASE/USER_END`、`build.sh` 的 `-Ttext`、
MMU 页表的 identity map 范围、`l3_user` 等页表映射、所有 EL0 用户程序测试。
风险面大，只有在方案 1 仍不够时才考虑。

### 方案 3（不推荐）：减小 32 KB 内核栈

把栈减到 28 KB 可以直接把余量拉回 8 KB，最简单，但内核栈变浅，方向与
「为后续功能铺垫」相反；历史上栈已从 64 KB → 40 KB → 32 KB 一路收紧，
再减需要重新评估最坏调用深度。**本次明确不采用**。

## 七、一句话总结

> 4 KB 余量是**安全预算**，不是 bug；真正的问题是「余量变化不可见」。阶段三
> 用分段预算表 + 三级阈值 + 团队基线 delta + 越界拦截实证把它变成可观测、
> 可预警、可拦截的工程机制，后续每加一个功能都能立刻看到自己吃掉了多少空间。
