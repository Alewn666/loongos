## 第十一轮（2026-10-24 晚）：真机（飞牛 KVM 虚拟机）跑通 —— GICv3 + 图形输出 ✅

### 背景
第十轮的 ISO 在本地 QEMU 全过，但用户在飞牛虚拟机上只见 `[stub] ...` 那几行，
之后黑屏、CPU 99%。逐轮排查后确认是**两个独立问题叠加**。

### 问题 1（致命）：内核把 GICv2 写死，用户机器是 GICv3
- 现象：GIC 初始化时数据中止，`FAR_EL1=0x08010004`（= GICC_BASE+4，GICv2 的 CPU 接口）
- 本地复现：`-machine virt,gic-version=3` 稳定复现（`ESR EC=0x25`）
- 根因：GICv3 里 `0x08010000` 这段 GICv2 的 CPU 接口**根本不存在**
- 修法：`gic_init` 探测版本并分流
  - ⚠️ **探针坑**：GICv2 的 `GICD_PIDR2` 在 `0xFE8`，**GICv3 在 `0xFFE8`**
    （64KB 帧的最后一页）。只看 `0xFE8` 会读出 0 → 误判成 GICv2 → 照样崩
  - GICv3 用系统寄存器收发中断：`ICC_SRE_EL1 / ICC_PMR_EL1 / ICC_IGRPEN1_EL1 /
    ICC_IAR1_EL1 / ICC_EOIR1_EL1`
  - SPI33（串口）配 `GICD_IGROUPR/ISENABLER`；PPI30（定时器）配 **redistributor**
    `GICR_*`（GICD 管不到 PPI）
- 顺带加固：stub 里补 **D-cache 清理**（KVM 真实 CPU 缓存是开的，不清则内核读到旧数据）
  和 **EL2 MMU 关闭**（KVM 下 stub 可能仍在 EL2）

### 问题 2：虚拟机窗口显示的是图形控制台，内核写的是串口
- 诊断方法：stub 里同时往 `ConOut` 和 `PL011` 写标记，同一行后写覆盖先写
  - 用户回报看到 `CONOUT-111`（不是 `PL011-222`）→ **确认显示通道是 GOP**
- 真机配置（从 `ps` 读到用户虚拟机的 QEMU 参数）：
  `-machine virt-7.2,gic-version=3 -accel kvm -cpu host -m 512
   -device ramfb -device usb-kbd -vnc unix:...`（**没有串口控制台**）
- ramfb 有真实帧缓冲（virtio-gpu 的 Blt-only 模式则 `FrameBufferBase=0`，不可直写）
- 修法：内核加**帧缓冲文字输出**
  - stub 取 GOP `Mode->Info`，把 base/宽高/stride/像素格式填进 `bootinfo`，用 `x0` 传给内核
  - `bootinfo` 放在 stub 的 `.data`（映像在 ExitBootServices 后仍驻留内存）
  - 内核 `uart_putc` 里镜像一份到 `fb_putc`（重定向期间不画，与串口语义一致）
  - `mmu_init` 末尾按 2MB 块补帧缓冲映射（Device 属性）
  - **中文**：`font8x16.h`（ASCII，取自系统 PSF1 字体）+ `font_cjk.h`
    （635 个汉字，用 `DroidSansFallbackFull.ttf` 经 PIL 渲染成 16×16 点阵，二分查找）
  - 帧缓冲侧做 UTF-8 解码，串口仍是原始字节
  - 启动时清屏（否则叠着 UEFI 的旧文字）

### 连带踩的坑
- 🔴 **加字库后内核撞进用户区**：`.bss` 末尾涨到 `0x401C1010` > `USER_BASE=0x401C0000`
  → `mmu_init` 断言"内核镜像撞进用户区，停机"。把 `USER_BASE` 提到 `0x401D0000`。
  **以后加大数组/字库都要回头看一眼 `__bss_end`。**

### 验证
- 串口路径：`test_iso_boot.py` GICv2 **12/12**、GICv3 **12/12**
- 图形路径：`-device ramfb` + VNC 截图，屏幕完整显示中文横幅/各阶段信息/shell 提示符

### 未做（重要）
- **键盘输入还不支持**：真机键盘是 `usb-kbd`（xHCI），需要 USB 驱动；
  当前只能"看见"，不能"打字"。下一步要么写 USB HID 驱动，要么给虚拟机加串口控制台。

## 第十轮（2026-10-24 傍晚）：阶段 5 ⑤ —— UEFI ISO 引导全部打通 ✅

### 干了什么
让灵珑系统**能从一张 UEFI ISO 光盘启动**（不再依赖 QEMU `-kernel` 直载）。
真机验收：QEMU + AAVMF 固件挂 `-cdrom iso/loongos.iso` → 固件加载 `BOOTAA64.EFI`
→ stub 读同卷 `kernel.elf` → 跳内核 → **横幅 + shell 全部正常**，
`test_iso_boot.py` **11/11 全过**（含 whoami/ls/cat/重定向）。

### 核心结论：整条链卡住的真凶是「PE 映像残缺」，不是 El Torito
排查顺序与证据（前面几条全是被误导的死胡同，记下来免得再走）：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| FAT 镜像里文件没放对 | `mdir -i esp.img ::` + `cmp` | ❌ 路径 `/EFI/BOOT/BOOTAA64.EFI` 正确、逐字节一致 |
| NVRAM 里有旧的失效引导项 | 每次 `rm` 后用全新 `AAVMF_VARS.fd` | ❌ 换新 NVRAM 仍同样报错 |
| AAVMF 只挂 ISO9660 树、不读 El Torito FAT | 把真实文件也铺进 9660 树重测 | ❌ 照样 Not Found |
| El Torito 目录本身坏了 | `xorriso -report_el_torito` | ❌ 目录正确（UEFI 平台、无仿真、LBA 正常） |
| **`BOOTAA64.EFI` 不是合法 PE** | **按字节解析 PE 头** | ✅ **真凶** |

**具体病象（objcopy 在 aarch64 上的真实缺陷）**：
- `SizeOfOptionalHeader = 0` → 生成的其实是 COFF 目标文件，不是 PE 映像
- 即使补 `--set-start` 让可选头出来，仍然 `Subsystem=0`、无 `.reloc` 段、
  带着 `IMAGE_FILE_RELOCS_STRIPPED` 标志且 `ImageBase=0`
- EDK2 固件看到"不可重定位 + 要装到地址 0" → 直接返回 `Unsupported`
  （初始版本因入口/可选头都缺，固件报的是 `Not Found`）

**为什么普通 `--target=pei-aarch64-little` 救不了**：binutils 2.40 只做
ELF→PE 的**段搬运**，不会把 ELF 的 `R_AARCH64_RELATIVE` 转换成 PE 的
`.reloc` 基础重定位表。而 gnu-efi 用的是"运行时自搬"模型（`_relocate`），
两者语义不匹配。

### 最终解法：自己生成合规 PE（`build_pe.py`）
不复用 objcopy 的 PE 输出，直接按 PE32+ 规范手工构造：

1. **读 ELF 的 PT_LOAD 段**拿到从 vaddr 0 起的完整扁平映像
2. **整体平移 `+0x1000`** —— 因为所有 `adrp/adr` 都是 PC 相对的，
   整体平移不改变任何相对距离，**内核与 stub 代码一行都不用改**
3. **从 ELF 的 SHT_RELA 段收集 157 条 `R_AARCH64_RELATIVE`，生成真正的
   `.reloc`**（`IMAGE_REL_BASED_DIR64`，按 4KB 页分组）
4. **清掉 `RELOCS_STRIPPED`**（Characteristics `0x0202`）并写
   `DataDirectory[5]` 指向 `.reloc` —— 让固件按"可重定位映像"加载
5. **把 `_start` 里的 `bl _relocate` 改成 `mov x0, #0`**：固件已经搬过一次，
   gnu-efi 的运行时自搬再搬一次就是**双重位移**，必崩

### 本轮踩的 4 个坑（都有实证，通用）

1. 🔴 **ELF64 头字段偏移记错**：`e_shentsize` 在 **0x3A**、`e_shnum` 在 0x3C
   （不是 0x3A/0x3C 写成 `e_shentsize,e_shnum`）。写错导致段表全错位，
   读出来的 `sh_offset=0x6000000000` 一眼假。**校验办法：读出来先看数值像不像**。
2. 🔴 **`mov x0,#0` 不能换成 NOP**：`_start` 里 `bl _relocate` 之后紧跟
   `cbnz x0, ret` —— x0 必须是 0 才会走到 `efi_main`。打 NOP 的话 x0 还留着
   前面 `adr x0, ImageBase` 算出的装载地址 → 条件分支跳走 → **永不进 main**。
3. 🔴 **gnu-efi 的 `gBS/gST` 必须靠 `InitializeLib` 赋值**：`efi_main` 开头
   不调 `InitializeLib(ImageHandle, SystemTable)` 就直接 `gBS->HandleProtocol`，
   拿到的是空指针 → 跳到数据段 → `Synchronous Exception at 0x407390A8`。
   **这是 stub 第一次跑起来后崩溃的唯一原因**。
4. 🟠 **重定位存储值要跟着平移**：ELF 语义 `*(site) = load_base + addend`，
   实测 site 里存的正是 addend；PE 加载器做 `*(site) += load_addr`。
   整体平移 0x1000 后，site 的初值必须先预设成 `addend + 0x1000`，
   否则所有 GOT 指针偏 0x1000。**验证方法：抽查若干 site，比对
   `stored == addend` 后再看平移后的值**。

### 结构变化
- 新增 `build_pe.py`（ELF → 合规 PE32+，含 .reloc 生成）
- 新增 `build_image.sh`（ELF → arm64 Linux Image，备用路径，当前主线不用）
- 新增 `test_iso_boot.py`（真机 ISO 冒烟 11 项）
- `build_stub.sh` 第 3 步改为调用 `build_pe.py`
- `build_iso.sh` 改为「双层铺」：ISO9660 树放真实文件 **+** 同时嵌 El Torito FAT
- `uefi_stub.c` 补 `InitializeLib`（关键修复）

### 验证
- `test_iso_boot.py`：**11/11 全过**（ISO 启动 → 横幅 → MMU/FS/权限就绪 →
  shell → help/whoami/ls/cat/重定向）
- `test_stage5d_redirect.py`：**31/0**（`-kernel` 直载路径未受影响）
- ISO 大小 4.6MB，`iso/loongos.iso`

### 没修的 / 待办
- 飞牛虚拟机是否支持 UEFI 启动仍待用户在界面上确认（ISO 侧已就绪）
- 真正的"安装到磁盘"要等阶段 6（virtio-blk 持久化），当前是内存盘，断电即失

## 第九轮（2026-10-24 下午）：阶段 5 ④ —— 重定向 ✅

### 干了什么
- **输出重定向 `cmd > 文件`**：`uart_putc` 是唯一总闸——`redir_on` 期间 shell 命令的打印先进
  2KB `redir_buf` 不上串口，命令跑完 `redir_finish()` 一次性落盘（覆盖写）并回报字节数；
  超 2048 字节截断并标 `redir_of`。覆盖 `cat/ls/df/help/run`——**EL0 用户程序经 svc 的输出
  也被一起抓进文件**，不泄漏串口。
- **输入重定向 `write 目标 < 源`**：`<` 文件整份读进 2KB `stdin_buf`（≤2047 字节），
  目前只有 write 消费（= 顺带实现文件复制，多行文件按字节走）；其他命令吃 `<` 明确报"不支持"。
- **解析器 `redir_parse`**：`>` 和 `<` 必须独立成词、各只一次、后面紧跟路径，否则报语法错；
  命令部分重装成单空格规范串再拆首词/参数。
- **worker 心跳在重定向期间闭嘴**（`!redir_on` 门）——防抢占时把心跳写进文件。
- **未知命令的抱怨收闸后才发串口**（相当于 stderr，不进文件）。
- `help` 新增重定向说明；文件头注释同步。

### 本轮修的 3 个真 bug（全有实证）
1. 🔴 **`redir_parse` 方向变量复用**：找目标词时 `s = p` 重赋值后还拿 `(*s == '>')` 判方向——
   判的是**目标词首字符**（`/`）→ 所有 `> 文件` 被误判成 `< 输入`，去加载不存在的输入文件提前返回。
   这是第一轮 **19 条断言全挂**的总根因。修：符号先存 `char dir = *s`。
2. 🔴 **dispatch 的输入支持检查拿整行比首词**：`fs_strcmp(cmd, "write")` 拿整条命令行
   （`"write /cp1"`）比 → 永远不等 → `write 目标 < 源` 被误拒。修：拆词后拿首词 `cmdw` 比
   （检查挪到拆词之后）。
3. 🔴 **`el1_landing` 抛弃 dispatch 栈帧（最隐蔽）**：`run` 的 exit svc eret 直达 `el1_landing`，
   它**直接递归进 `shell_loop()` 永不返回** → `redir_finish()` 根本没机会跑、闸门常开，
   把后续提示符和下一条命令的输出全吸进文件（实测 `df` 的输出就这么进了文件、串口上消失）。
   证据：`qemu -d int` 抓到 run 的 4 个 SVC（3 write + 1 exit）证明程序早就跑完，
   shell 却在 `shell_loop+0x4c` 的 `wfi` 空转——所谓"6 秒延迟"是假象，其实是
   "直到下一条命令的 dispatch 末尾才被顺手冲刷"。修：`el1_landing` 进 shell 前补
   `redir_finish()`（幂等，`redir_len<0` 直接返回；fault 路径走同一着陆点，一并覆盖）。

### 另有 2 处是测试期望写岔（改测试、不改内核）
- root 切 demo **本就免口令直切**（阶段5① 设计如此），测试却在等"口令"提示；
- `whoami` 实际格式是 `demo (uid=1000)`，不是我写的 `demo(1000)`。
沿用上轮教训：**没顺着坏期望去"修"好内核**——先抓原始串口转录定位再说。

### 验证（均可重跑）
- 新套件 `python3 test_stage5d_redirect.py` → **31/31**（五类命令落盘、输出不泄漏串口、
  语法错两态、`<` 三态、DAC 拒写、stderr 语义、cwd+心跳回归）
- 回归：`test_stage4_fs.py` **28/0**、`test_stage5_qemu.py` **35/35**、
  `test_stage5b_elf.py` **33/0**、`test_stage5c_cwd.py` **20/0**、KAT **9/9**
- 排障利器复用：`qemu-system-aarch64 … -d int -D int.log`（本轮定位 el1_landing 的关键证据）

### 未修 / 已知债务 / 待拍板
- `el1_landing → shell_loop` 递归导致**每次 `run` 留一层废弃栈帧**（阶段5② 起就有；
  教学场景跑几次无碍，根治要把 run 改成"返回 dispatch"的结构，动静大）
- 重定向输出上限 2048 字节（大文件等阶段 6 磁盘）
- **ISO 引导线待拍板**：用户问"什么时候出能跑虚拟机的 ISO"——已答复需新阶段
  （UEFI stub + grub-mkrescue 打 ISO9660，aarch64 估 1~2 周末；x86 VirtualBox 需移植不现实），
  要不要立成阶段 5⑤ 等用户点头

## 第八轮（2026-10-24 晚）：阶段 5 ③ —— cwd + 相对路径 ✅

### 干了什么

- **验证**：新套件 `test_stage5c_cwd.py` **20/20**（pwd 初值/绝对/相对/.·..折叠/相对 write·ls·cat·
  run/拒非目录/拒不存在/cd 无参回根/DAC 回归/心跳自愈）；回归 `test_stage5b_elf.py` **33/33**、
  `test_stage4_fs.py` **28/0**、`test_stage5_qemu.py` **35/35**。

### 本轮踩到的坑（2 测试坑 + 1 认知纠正）
1. **🟠 `edit_file` 的 old_text 撞了两个位置，整块代码被插了两遍**：`static void cmd_ls(char *a)`
   在**声明表**和**定义**处各出现一次，我拿它当锚点插 cwd 块 → 重复定义直接编译失败
   （而且报错行号指向第二份，第一份还安静地排在声明表前面）。修：`sed` 按行号删掉第一份。
   **教训：拿函数签名当插入锚点，先 `grep -c` 数出现次数；出现≥2 就换更独特的锚（如函数体第一行）。**
2. **🟡 隐式声明坑（C 老坑复现）**：`run_userprog`（第464行）调 `path_resolve`，而定义在1000+行的
   shell 段——没前向声明 → C 隐式 `int path_resolve()` → 与后面的 `static` 定义冲突报错。
   修：在 ELF 段前补 `static int path_resolve(...);` 前向声明。
3. **🟡 "root 免口令"的语义**：指 **root 切别人**免口令；**demo 切 root 要 root 的口令**。
   测试最初以为 `su root` 免密直切，结果 `crash udf` 整条命令被当口令吞掉 → "内核自愈"断言假红。
   排查方法：把失败断言那个时间窗的原始串口字节 `repr()` 出来，一眼看到 `口令不对`。
4. **🟡 串口流是 `\r\r\n`**（pty 本地回显 + 客人回显叠加）：测试 harness 里
   `replace(b"\r\n", b"\n")` 只做一次会剩一个 `\r`，带换行的 needle（如 `"/home\n"`）全假红。
   修：归一做两次（`test_stage5c_cwd.py` 已固化，写新测试照抄这个 harness）。

## 第七轮（2026-10-24 晚）：阶段 5 ② —— ELF 加载器 + 用户程序 ✅

### 干了什么
- **用户程序体系（`user/` 三件）**：`user.h`（syscall 内联封装：`sys_call/sys_exit/u_puts`，
  x8=号、x0/x1=参、返回 x0）；`hello.c`（走 syscall 打三行字后 `exit(0)`）；
  `bad.c`（反面教材：①拿内核地址调 sys_write → 内核拒返回 -1 ②不走 syscall 直读内核 → 被杀）。
- **构建链（build.sh）**：`gcc -nostdlib -static -Ttext=0x401C1000 -z max-page-size=0x1000
  --build-id=none` 编独立 ELF → `objcopy -I binary -O elf64-littleaarch64 -B aarch64`
  把 **ELF 文件本身**嵌成 blob（符号 `_binary_<名>_elf_start/_end`）→ 随内核链接。
  开机 `seed_userprogs()` 用 `fs_createfile/fs_setfile` 写进 `/bin/hello`、`/bin/bad`。
- **内核 ELF 加载器（kernel.c `run_userprog`，新命令 `run <路径>`）**：
  校验 magic→phdr 不越界→入口与所有段必须落在用户区→**先把整个用户区恢复 USERRW**
  （坑 ①，见下）→逐段 `fs_memcpy`+bss 清零→按段标权限（PF_X→PROT_USEREX 否则 PROT_USERRW）
  →`DC CVAU`+`IC IVAU` 冲 I-cache（真机必需，QEMU 看不出）→`tlbi vmalle1`→
  `enter_el0_at(entry, USER_END)` eret 进 EL0（SP_EL0=用户栈顶=USER_END）。
  手写 ELF64 Ehdr(64B)/Phdr(56B) 结构体（不依赖工具链头文件，字段布局按 ABI 核对过）。
- **syscall 分发（`svc_dispatch`）**：`user_running` 标志区分「用户程序」vs「el0 演示」：
  x8=0 write——指针必须在 `[USER_BASE, USER_END)` 且不溢出，越界打印"用户指针越界，拒绝"返回 -1；
  x8=1 exit——打印退出码，`spsr=EL1h`、`elr=el1_landing` 撤回内核重新接管 shell；
  未知号返回 -1。用户程序跑飞（EC 0x20/0x24 来自 EL0 且 user_running）→ 打印出错现场**杀掉回 shell**
  （不学 ELR+4 纵容——那是给内核演示自愈用的，用户代码必须隔离处置）。
- **用户区**：`USER_BASE=0x401C0000`、`USER_END=0x40200000`（256KB，内核 2MB 区顶部，
  复用 l3_kern/fill_l3；代码段 EL0 RX+PXN、data/栈 EL0 RW+UXN；`enter_el0` 拆成通用
  `enter_el0_at(elr,sp)`，el0 演示与 run 共用）。
- **验证**：新套件 `test_stage5b_elf.py` **33/33**（种子/help/ls、hello 全链路、bad 两道防线、
  非 ELF 与不存在拒跑、el0 演示回归、crash 自愈、whoami）；回归 `test_stage4_fs.py` **28/0**、
  `test_stage5_qemu.py` **35/35**、crypto 主机 KAT **9/9**。

### 本轮抓到的问题（3 个：2 构建坑 + 1 真 bug）
1. **🔴 上一个程序的代码段会让下一个程序装载时炸（真 bug，bad 程序首跑抓到）**：
   代码段标 `PROT_USEREX`（AP=EL0 独占）后 **EL1 也写不了**；装第二个程序时 loader 的
   `fs_memcpy` 从 EL1 写 → 数据中止 → ELR+4 自愈 → 写指针 +8 继续 → **无限异常风暴刷屏**
   （FAR 逐 +8，一次转储上千行）。第一个程序没事只是因为页还是开机的 USERRW。
   修法：装载前 `fill_l3(USER_BASE,USER_END,PROT_USERRW)`+TLB 冲刷整体恢复可写，装完再按段收紧。
2. **🟠 用户区选址撞 fs_disk（构建期断言抓住）**：最初把用户区放 0x40100000（以为是内核镜像后的空地），
   实测 `__bss_end=0x401B7010` 直接撞进去——**fs_disk（1MB 内存盘）本身就是 .bss 里的静态数组**。
   mmu_init 的"镜像撞用户区就停机"断言当场拦下（宁可停机也不带病运行）。
   现址 0x401C0000 在 bss 之后，余量 ~36KB，再长镜像要把 USER_BASE 上挪（上限 0x40200000）。
3. **🟡 用户 ELF 的段基座被 64KB 对齐拽出用户区（构建期 readelf 抓到）**：默认 ld 把
   PT_LOAD 基座按 max-page-size=64KB 对齐（0x400F0000/0x400FF000 都低于 USER_BASE）；
   `.note.gnu.build-id` 还额外生成一个 0x400000 的 R 段。修法三连：
   `--build-id=none`（删 note 段）+ `-z max-page-size=0x1000` + `-Ttext=USER_BASE+0x1000`
   （留出 ELF 头所在页）。**验证方法 = `readelf -l` 看 PT_LOAD 的 VirtAddr**，只看文件能编过不算数。

## 第六轮（2026-10-24 傍晚）：阶段 5 ① —— root 与权限基建 ✅

### 干了什么
- **新增 `crypto.c`/`crypto.h`**：SHA-256（FIPS 180-4 标准算法）+ 迭代哈希 `sha256_iter`
  （PBKDF1 风格：先 SHA256(salt‖pw)，再迭代 N-1 趟 SHA256(上趟‖salt)）+ `to_hex`。
  build.sh 变四件套：`boot.o kernel.o fs.o crypto.o`。
- **fs 层 DAC（`fs.h`/`fs.c`）**：inode 加 `uid`（属主）+ `mode`（`FM_PRIVATE` 私密位），
  布局仍 128B（u64 必须紧跟 indirect，uid/mode 塞在尾部，坑见下）；新增当前操作者
  `fs_setuid/fs_getuid` + 规则：**改/删 = 属主或 root；建文件/目录 = 父目录属主或 root；
  读默认公开，FM_PRIVATE 只许属主和 root**；错误码 `FS_DENIED(-2)` 与 `-1` 分开返回。
  新 API：`fs_chown` / `fs_chmod` / `fs_inode_uid`。
- **身份三件套（kernel `auth_init()`，开机建）**：
  `/etc/passwd`（`name:uid`，可读）；`/etc/shadow`（`name:盐hex:哈希hex:迭代数`，
  **只存哈希绝不存明文**，`fs_chmod(FM_PRIVATE)` 私密）；`/home/demo`（fs_chown 给 demo）。
  默认口令（教学，横幅打印）：root=`loong2026`、demo=`demo2026`；迭代 2000 轮。
- **新命令**：`whoami`（uid→名字反查 passwd）；`su [用户]`（`blocking_getline` 阻塞等输入、
  **口令不回显**；**root 切谁都免口令**，非 root 要过 `shadow_verify`；
  su 临时 `fs_setuid(0)` 特权读 shadow——同 Unix 里 su 是特权程序 setuid root 的道理）。
  `cat/write/mkdir/rm` 错误提示按 `FS_DENIED` 分级（"权限不够" vs "不存在/盘满"）。

### 本轮抓到的问题（3 个：1 真 bug + 2 测试错）
1. **🔴 SHA-256 尾块填充 off-by-one（真 bug，FIPS 向量当场抓住）**：填零个数写成
   `56-rem`，正确是 `55-rem`（0x80 本身占 1 字节）。症状：短消息哈希全错、
   **空串"碰巧"对**（长度场内容是 0 被截断后仍是 0，还越界写 4 字节出栈）。
   写哈希算法这种"有标准答案"的东西，**必须先上标准测试向量再往下走**——
   KAT 一跑 2/3 挂，5 分钟定位；要是没有 KAT，这 bug 会一路潜伏到口令校验全军覆没。
2. **🟡 测试期望与设计不符（测试错，内核对）**：第一版端到端测试等 `su demo` 弹口令提示，
   但设计就是 **root 免口令直切** → 密码被打成命令回显，时序区一片假红。
   排查靠**直接抓原始串口转录**（分段打印 buffer），一眼看到"现在是 demo"没有口令提示。
   ⚠️ 教训：交互测试连续失败时，先 dump 原始转录再改代码——别顺着坏期望去"修"好内核。
3. **🟡 任务表断言凭印象写错**：`show_tasks` 用 `uart_puthex` 打编号 → 输出
   `task0x0000000000000001`，断言写 `[task] task1`/`[task] 1` 都落空。
   已有 TODO 老规矩：**测试期望值别凭印象，写完逐条手工复核**。
4. ⚠️ 防自伤：第一次写 `test_crypto.c` 时一段转义垃圾混进文件（已重写干净版）；
   `run_tool_batch` 的 actions JSON 在本环境两次报 "not valid JSON"——改为逐条 edit_file。

## 第五轮（2026-10-24 下午）：阶段 4 —— 文件系统 + 行模式 shell ✅

### 干了什么
- **新增 `fs.h`/`fs.c`**：Unix 式单根 `/` 极简文件系统，1MB 内存盘（256×4KB 块）。
  经典三层：block0 superblock（magic="LOONGOS"）+ block1 空闲位图 + block2..5 inode 表（128 个 ×128B）+ block6.. 数据区。
  inode = 10 直接块 + 1 间接块（512 项）→ 最大文件 2MB+40KB；目录 = 定长 64B 目录项（`{u16 inum, char name[62]}`），
  空槽复用 + 长满追加块；`nlink`、`mtime=tick/10`。演示数据：`/etc/hostname`、`/home/readme.txt`（中文）。
- **内核拆出第二个编译单元**：build.sh 编 `boot.o + kernel.o + fs.o` 三件套链接。
- **shell 升级行模式**：行缓冲 + 退格（`\b`/0x7f → `\b \b`）+ 命令分发表。
  命令：`ls [路径]` `cat` `write <路径> <内容>` `mkdir` `rm`（文件或空目录）`df` `help`，
  老功能收编：`mmu` `tasks` `el0` `crash udf|brk|abort|wronly`。
- boot.S 降级到 EL1 后打开 FP/NEON（CPACR_EL1.FPEN=11）；内核栈 16KB→64KB（linker.ld）。
- `tasks` 输出加「任务表」表头；运行中任务不再显示已消费的旧帧 ELR（原来显示的是栈复用后的垃圾）。

### 本轮抓到的 4 个 bug（前 3 个都是"裸机 + freestanding"的经典大坑）
1. **没开 FP/NEON → EC=0x07 未定义异常**。GCC 把 `fs_memset(fs_disk, 0, 1MB)` 自动向量化成
   `movi v0.4s`（NEON），而 CPACR_EL1.FPEN 默认全 trap → 一进 fs_init 就崩（崩溃转储
   EC=0x07、ELR 正好在 fs_init 第二条指令）。修：boot.S `msr cpacr_el1, #(3<<20)` + isb。
   ⚠️ 汇编里寄存器名是 `fpsr`/`fpcr`，**不带 `_el1` 后缀**（写错汇编器直接报错）。
2. **栈上 4KB 块缓冲打爆 16KB 内核栈**。`cat → fs_readfile → fread_bytes(blk[4096]) → bmap(iblk[4096])`
   三层嵌套 >16KB，表现为各种诡异路径错误（根 inode 读成垃圾、lookup 全灭）。
   修：fs.c 全部改用**单块静态 scratch**（嵌套审计：每次 bread(scratch) 后立即把数据拷出，
   无函数跨"另一次 scratch 使用"持有其中数据；前提=只有 shell 串行调 fs，worker 要用必须先加锁），
   balloc 清零改用 .rodata 的 `fs_zero` 零块模板；栈同时加宽到 64KB 双保险。
3. **strict-aliasing 类型双关在 -O2 下炸**（最难查）。`*out = *(struct inode *)(blk+off)` 读一个
   刚经 u64 写入的字节缓冲——GCC -O2 认为两种类型不别名，把读优化掉。
   **宿主机编译（-O0）全绿、内核 -O2 立刻复现**"inode 全是垃圾"。
   修两层：iget 改 `fs_memcpy` 拷出（字节拷贝永远安全）+ build.sh 全局加 `-fno-strict-aliasing`
   （内核标准做法，Linux 也这么编）。
4. **`bwrite(b, &短结构体)` 栈越界读**（自审抓的，未上机）：bwrite 永远写满 4KB，
   对 24B 的 super / 64B 的 dirent 指针直接写会把栈上邻居一起写进盘块。
   修：所有整块写一律先进 scratch 垫齐。

### 方法论教训（同样值钱）
- **交互测试断言会被命令回显污染**：第一版 UI 断言 `cat readme 含"第一个文件"` 匹配到了
  自己打进去的命令字母、`ls /` 的 "etc/home" 甚至匹配到横幅——一片假绿。
  修：测试按"每条命令前的缓冲区水位"切片 + 剔除该命令的回显前缀。
- **测试期望值不能凭印象写**：`ESR=0x21`（实际打印全宽 hex）、`mmu 已开启`（实际输出 SCTLR…）、
  退格测试算错字符数——三条都是测试自身错，被逐条手工复核抓出。
- **`u32 arr[N] = {0}` 在 freestanding 下生成 memset 调用 → 链接炸**（`undefined reference to memset`）。
  大数组一律不写 `= {0}`，需要清零就走 fs_zero/fs_memset。

### 证据（2026-10-24 实测）
- **内核交互全量 `python3 myos/test_stage4_fs.py`：28/0 全绿**（真 pty 喂键盘）：
  启动自检（root type=1）→ ls/cat 中文内容 → write/覆写/读回 → mkdir/rm（非空目录拒删）→
  df → 退格改错 → 未知命令 → mmu（M=1）→ crash udf 转储+自愈 → EL0 往返 → worker 心跳仍在。
- **宿主机压测（fs.c 直接 gcc 编译跑）`/tmp/myos_fs_host/stress`：8/8**：
  50KB 大文件（13 数据块+1 间接块）写读 memcmp 一致、块用量精确（+14）、截断回收到 +1、
  删除回收到初始、批量建 30 文件全命中。
- fs 逻辑在宿主机（-O0）与内核（-O2）行为一致（修 aliasing 之后）。

### 未修/已知现象（写给后轮）
- **fs 单 scratch 无锁**：worker 现在不碰 fs，所以安全；阶段 5 若让多任务写文件必须先加 fs 信号量。
- **`..` 不做环检测**：`mkdir /a` → `mkdir /a/b` 后没有把 /a/b 挂进循环的操作路径，暂无风险；
  做硬链接/链接数回收时要一并考虑。
- **rm 不回收父目录的 nlink**（目录 nlink 纪律松），教学版可接受。

- 目录项 >64 个触发"追加块"路径在内核里没直接测（宿主机测过逻辑），内核侧 mkdir 30 次即可覆盖。

## 第四轮（2026-10-24 中午）：阶段 3 —— 定时器 + 抢占式多任务 ✅

### 干了什么
- **ARM Generic Timer（物理定时器 PPI30）**：读 `CNTFRQ_EL0`（实测 0x3B9ACA0=62.5MHz）→
  `cntp_tval_el0` 重装 → 10Hz 抢占；GIC 侧 `GICD_ISENABLER bit30` + 优先级；
  **EOIR 条件从 `id>=32` 改成 `id>=16`**——PPI（30）也要 EOI，否则中断永远停在 in-service
  只会被响应一次（串口是 SPI33 不受影响，这坑只在上 PPI 后才暴露）。
- **抢占式上下文切换（异常帧换栈法，Linux arm64 同款）**：`handle_irq` 改为
  `struct regs *handle_irq(frame)`——定时器中断里 `task_switch`：当前帧指针记回它自己的
  栈（`tasks[cur].frame`），换上下一个任务的帧指针返回；`boot.S` 的 `irq_entry` 在 `bl` 后
  加一行 `mov sp, x0` 即完成切换（sync 路径不动）。
- **任务表 + 造帧**：task0=kernel/shell（帧在首次抢占时自然生成）；task1=worker，
  `task_create` 在它的栈顶伪造一个"初始异常帧"（ELR=task1_main、SPSR=0x345=EL1h+IRQ开），
  `RESTORE_CTX` 一恢复就等于从异常返回进函数——**无需任何手写入口汇编**。
- **新命令 `t`**：tick、当前任务、每任务被调度次数、帧地址、上次抢占点 ELR。

### 证据（全功能回归实测，约 24s 一发跑完）
```
[time] Generic Timer freq=0x3b9aca0 (62.5MHz)，10Hz 抢占式轮转
[task1] 心跳 slice=0xa/0x14/0x1e/0x28...0x6e  ← 精确每 10 片一次，tick 间隔恒 0x14
t → task0 调度 0x13 次 帧=0x4008fe30 上次抢占点 0x40080f90(shell wfi)
    task1 调度 0x13 次 帧=0x40085f80 上次抢占点 0x40080bbc(心跳 wfi)  ← 交替轮转
打字回显正常（含与心跳行交错）；d/w/e 三连演示全过（含 [来自 EL0] EC=0x24 SPSR=EL0t）
[el0] SVC landing → shell 恢复 → task1 心跳继续（EL0 往返不影响任务表）
```

### 本轮抓到的 2 个 bug
1. **`tasks[1].stack_top` 忘赋值** → `task_create` 拿 `0-288` 当帧地址 → 开机即数据中止
   （FAR=0xfff…fee0，负数栈顶一眼定位）。修：`&t1_stack[sizeof(t1_stack)]`。
2. **心跳永远不打（逻辑坑，非代码错）**：严格轮转下 **task1 只能看到奇数 tick**
   （task0 吃偶数片，启动对齐所致），`tick % 10 == 0` 永远不成立。第一版心跳 50+ 片零输出。
   修：改数"自己跑了几片"（`slices % 10`），与 tick 奇偶解耦。
   **教训：多任务里凡是"周期性"判断，别拿共享 tick 当自己的节拍——轮转相位会骗人。**

### 未修/已知现象（写给后轮）
- 轮转是"每 tick 必切"的最朴素调度；shell 与 worker 同权重——阶段 5 有了用户程序再谈优先级。

## 第三轮（2026-10-24 中午）：阶段 2 —— MMU 分页 + 权限隔离 + EL0 用户态 ✅

### 干了什么
阶段 0/1 基础上新增（`kernel.c` ~520 行、`linker.ld` v2）：

- **4KB 粒度页表恒等映射**（物理=虚拟）：L1（1GB 档，39 位 VA 从 L1 起查）→ L2（2MB 档，
  设备 2 块 Device-nGnRE + RAM 63 块大页）→ 内核所在 2MB 区下钻 **L3 细分 4KB 页**；
- **权限分级**：`.text` EL1 只读可执行（UXN 挡 EL0）、`.el0text` EL0 可执行/EL1 不执行（PXN）、
  `.rodata` 双方只读、data/bss/栈/页表 EL1 读写、`el0_page` 读写给 EL0；
  设备（GIC 0x08000000 / UART 0x09000000）映射 Device 属性，空隙不映射（误访问=fault）；
- **开 MMU 标准序列**：MAIR（Attr0=0xFF Normal / Attr1=0x04 Device）→ TCR（T0SZ=25 起查 L1、
  TG0=4KB、SH0 inner、IPS 40bit、EPD1 禁 TTBR1）→ TTBR0=页表基址 → `dsb sy; tlbi vmalle1; dsb sy; isb`
  → SCTRL 置 M/C/I 位（恒等映射下原地下一段指令安全切换）；
- **linker PHDRS 三段**（R+X / R / RW）→ **阶段 0 遗留的 `LOAD segment with RWX` 警告清零**，
  并输出节区边界符号（__text_start 等）供页表填权限；
- **shell 新命令**：`m`=读回 SCTLR/TCR/TTBR0/MAIR+节区地址；`w`=写 .text（写保护演示）；
  `e`=eret 进 EL0 跑用户态演示代码；

  .text 被权限违规逮住 → EL1 转储打 **[来自 EL0]** → ELR+4 自愈回 EL0 ③回写 0xAC

### 本轮抓到并修掉的 5 个 bug（全在"开 MMU 那一瞬"，逐层推进式排障）
1. **T0SZ=16（48 位 VA）→ 硬件从 L0 级开始查表**，我只有 L1 表 → L1 级 translation fault 风暴
   （`-d int` 读 IFSC=0x05=level1 定位）。修：T0SZ=25（39 位 VA，起查 L1，表结构原样复用）。
2. **L3 填表漏了 VALID/TABLE/AF/SH 位**——prot 参数只传了 AP/XN/Attr 局部位 → text 页 L3 条目
   无效（IFSC 变 0x07=level3 确认推进了一级）。修：PROT_TEXT/EL0TX/RODATA 全位常量化。
3. **L2 块描述符带了 PTE_TABLE（bit1=1）** → 硬件把 `0x09000000`（UART 物理地址）当页表基址
   去查第三级，读寄存器当页表全是垃圾 → UART L3 fault。修：块=VALID 一位不带 TABLE
   （`PROT_DEV & ~PTE_TABLE`）。
4. **`fill_l3` 起点未按页对齐（本轮最难）**：`__data_start=0x400834c0`，`a | prot` 把 PA 低 12 位
   脏值拼进描述符 → **AP 位被污染成 0b11=只读** → MMU 一开所有 data/栈/页表页变只读 →
   第一次按键进异常时 `SAVE_CTX` 写异常帧就权限故障，嵌套降栈直到帧落在唯一可写的 el0_page
   才打出转储（转储里 x 寄存器全是页表变量残值，极具迷惑性）。修：fill_l3 起止各自向下/向上
   取整到页。**教训：PTE=地址|属性 的拼接里，地址必须已对齐，否则低 12 位会污染属性位——
   症状（转储寄存器怪、FAR 步进 0x10）和病因（一个没对齐的变量）离得非常远。**
5. **`enter_el0` 声明了 `spsr` 却忘了 `msr spsr_el1`** → eret 带旧 SPSR（EL1h）跑到 EL0 代码页，
   被自己设的 PXN（EL1 不可执行该页）逮成 EC=0x21 同级取指中止 → 停机。修：补寄存器写入。
   顺手修"来自 EL0"标记：判据是 EC 0x20/0x24（低 EL 中止的 EC 本身就分档），不是 ESR bit16（那是 ISV）。

### 本轮抓到并修掉的 7 个 bug（全是硬核知识点）
1. **向量表布局全错（本轮最难）**：aarch64 GAS 的 `.align 7` = 对齐到 **7 字节**（字节语义，
   不是 x86 的 2^7）；且 16 个槽必须各占 0x80——我把 16 条 `b` 挤成 64 字节。
   VBAR 硬件把基址低 7 位清零 → 基址偏 8B → CPU 在"槽位"读到**指令中间的字节**，
   解码成垃圾到处乱跑（打出貌似有意义的"半个转储"，极具迷惑性）。
   修：每个槽前 `.balign 128`。**教训：异常向量表必须逐槽对齐，症状（乱码输出）和病因（表布局）
   可以离得非常远——用 `qemu -d int` 看真实向量目标地址一秒定位。**
2. **`GICD_ISENABLER(n) = 1` 写错值**：这组寄存器每位管一个中断号，INTID33 在第 2 组里是 bit1，
   要写 `1 << (n%32)`；写 1 使能的是 INTID32。症状：中断永远不来。
3. **`daifclr` 无裸助记符**：正确是 `msr daifclr, #2`（MSR 写 PSTATE 字段）。
4. **QEMU pl011 中断位选错 → 中断风暴**：QEMU 里 `INT_TX=bit5、INT_RX=bit4`（我按反的用，
   使能了 TX 位）→ 串口每发一个字就中断一次；TXRIS 只有写 ICR 才清 → 死循环风暴。
   查证方式：给 handle_irq 打 IAR 身份 + 读 RIS（0x20=TX 位在断言）+ 读 QEMU 7.2 源码对表。
5. **绝不能写 `UARTICR=0x7FF` "清挂起"**：开机早期（banner 打印时）管道灌入的第一个字符已在
   1 字节保持寄存器里、RX 位置位——ICR 一写把这状态抹掉，而 QEMU 的置位条件是
   `count==trigger(1)` 的**边沿**，寄存器里的字符没人读走 count 回不到 1 → **接收死锁**，
   后续所有字符永远进不来（表现为"回显全灭"）。正确姿势：不开 TX 位就不用清，靠 IMSC 屏蔽即可。
6. **寄存器转储循环越界 UB**：`for(i=0;i<31;i+=2)` 打印 `x[i+1]` 时 i=30 → 访问 x[31]。
   GCC 的 -Waggressive-loop-optimizations 警告是对的。修：循环到 30、x30 单独打。
7. **构建输出被 grep 吃掉错误 → 旧 ELF 幸存**：`build.sh | grep error` 时链接/汇编失败没露面，
   QEMU 跑着上一版 kernel.elf，症状是"改了没生效"。修：构建前 `rm -f *.o kernel.elf`，
   别用管道过滤吞退出码（老朋友了：`| tail` 同款坑）。

### 已知现象（非 bug，写给后轮）
- **管道一次性灌入全部输入**（printf 在开机瞬间灌完）时，QEMU stdio-mux 的排队怪癖：
  第一个字符中断路径收掉，其余卡在 mux 里不来了（`wfi` 主循环下不回显）。
  **交互式打字（人类在终端敲）不受影响**——已用延迟逐段输入实测：每段按键独立触发 IRQ、
  回显和崩溃命令全部正常。自动化测试脚本要么用逐段延迟输入，要么别用 wfi 版做管道灌入。
- RX 是 1 字节保持寄存器（FIFO 关着）+ `can_receive=count<1`：字符一个一个放行，
  中断一个一个来——这是 QEMU pl011 无 FIFO 模式的正常行为。

## 第十四轮（2026-10-24 22:2x）：USB 键盘在 KVM 下必崩（数据中止）—— 后索引寻址触发 NISV ✅

### 背景
第十三轮修完心跳刷屏后，我开始做「USB 键盘」这条线（阶段 6 的先行件）：
`usb_kbd.c` 从零写 xHCI 驱动（PCI ECAM 枚举 → 控制器复位/启动 → 端口复位 →
Enable Slot / Address Device → GET_DESCRIPTOR → HID boot 键盘 → 中断 IN 端点），
`kernel.c` 补 PCIe 窗口 Device 映射，`test_kbd.py` 用 QMP `sendkey` 真敲字验证。

**TCG 一次全过**（`python3 test_kbd.py` ALL PASS：`help`/`whoami` 真执行、回显正常），
**KVM（用户飞牛虚拟机走的就是这条）必崩**：

```
** 内核异常: 数据中止 ***
ESR_EL1 = 0x0000000096000010  (EC=0x25)
FAR_EL1 = 0x0000000010100440   ← 用户机上 0x10800440（xHCI BAR+0x440）
ELR_EL1 = 0x0000000040089fb0   ← usb_kbd_init+0x550 的 ldr w3,[x1],#16
[自愈] ELR+4 跳过肇事指令，继续活着   ×8（8 个端口各炸一次）
[usb ] 没有设备接入
```

用 `virsh screenshot` 连到用户虚拟机的 VNC 截图，**屏幕上的报错与本地 KVM 复现逐字一致**。

### 排查过程（三个假设，前两个被证伪）
1. **假设「QEMU 没有这个 MMIO 区域」** → 用 monitor 的 `xp` 从 QEMU 侧直接读 guest 物理地址：
   `0x10100440` 返回 `0x000202a0`、`0x10100480` 返回 `0x00020ee1`（端口 5 有键盘）——**区域存在、数据正确**。
   另开 trace：KVM 下 `usb_xhci_cap_read` 命中 5 次、`usb_xhci_port_read` **0 次**；
   TCG 下 `port_read` 12 次。→ 访问**根本没送到设备模型**。
2. **假设「DMA 把页表冲了」** → 崩后从 QEMU 侧 dump 页表：
   `l2_dev[128] @0x400b0400 = 0x0060000010000705`（VALID|AF|SH_INNER|Device|PXN|UXN），
   邻域与 `l1_table[0]`/`l0_table[0]` 全对 —— **页表完好**，假设证伪。
   （关键矛盾：同一 2MB 块内的 `BAR+0x40` 读写正常、`BAR+0x440` 必崩，页表粒度上不可能区分。）
3. **正解：宿主机 KVM tracepoint**
   ```
   kvm_guest_fault: ipa 0x10100000, hsr 0x92000005, hxfar 0x10100440, pc 0x40089fb0
   kvm_mmio_nisv:  ipa 0x10100440, esr 0x92000005, far 0x10100440
   对照正常 UART 访问：hsr 0x93810006 → ISV=1
   ```
   `hsr=0x92000005`：EC=0x24（stage-2 数据中止）、ISV=**0**、DFSC=0x05。
   **ISV=0 = 指令综合信息不可用（NISV）**。

### 根因
MMIO 读被 GCC 强度削减成**后索引寻址** `ldr w3, [x1], #16`（循环里「读寄存器 + 指针前进」）。
带写回的加载/存储，硬件在 stage-2 中止里 **ISV=0** → KVM 走 NISV 路径 → QEMU 解不出这笔访问
→ **直接给 guest 注入一个 data abort**（composed ESR 的 DFSC=0x10，看着像"对齐错误"，
其实 0x440 对齐到 64 字节，硬件不可能真报对齐错）。

- 为什么只有它炸：**单次访问**（BAR 前段 CAPLENGTH/HCSPARAMS/USBCMD…）编译成普通 `ldr/str`，ISV=1 正常；
  只有**循环里的**访问被强度削减成写回形式。所以「同一页、前半段通、后半段崩」。
- 为什么 TCG 全过：TCG 不走 KVM 那套 stage-2/NISV 机制，访问直接进 QEMU。

### 修法
1. `usb_kbd.c`：`rd32/wr32` 改为**内联汇编单次 ldr/str**（编译器再也无法合并出写回形式）：
   ```c
   static u32 rd32(volatile u32 *p){ u32 v; __asm__ volatile("ldr %w0, [%1]" : "=r"(v) : "r"((u64)p) : "memory"); return v; }
   static void wr32(volatile u32 *p, u32 v){ __asm__ volatile("str %w1, [%0]" :: "r"((u64)p), "r"(v) : "memory"); barrier(); }
   ```
2. 所有 MMIO 访问点统一走它们：端口扫描循环、ERSTSZ/ERSTBA/ERDP、事件环 `p[0]=`/`p[1]=`（会合成 `stp`）、
   调试打印。文件里加了大段注释 + `grep` 自查规则（**禁止裸 `*(volatile u32*)` 解引用**）。
3. 测试脚本两处健壮化（都是测试自身问题，非产品）：
   - `test_kbd.py`：KVM/TCG 用各自的日志与 socket 路径（root 建的 `/tmp/kbd_serial.log` 会让普通用户那趟
     QEMU 直接 `Permission denied` 退出 → 表现为 `FileNotFoundError: kbd_mon.sock`）；
     回显断言先剔掉 `[task1]` 心跳行（心跳会插进输入回显中间，把 `help\n` 打断 → 假失败）。
   - `test_iso_boot.py`：重定向那项等待 2.5s → 4.0s（心跳挤占串口时 2.5s 不够，实测偶发只吐了一个 `r`）。

### 通用教训（写给以后的我，也适用任何裸机/KVM 工程）
1. **「TCG 过、KVM 挂」几乎总是真实的硬件语义差异**，别当成偶发。本案差在「MMIO 访问的 ISV 位」。
2. **裸机驱动里的 MMIO 一律用内联汇编单次 ldr/str**。让编译器在循环里做强度削减（后索引/`stp`/`ldp`），
   在 KVM/真机 + KVM 的 NISV 路径下会变成随机数据中止，而 TCG 永远暴露不出来。
3. **排障要用宿主机视角**：`kvm_guest_fault` / `kvm_mmio_nisv` / `kvm_mmio` tracepoint 一眼定位
   「访问死在 guest 还是死在 VMM」；再配合 `xp` 从 VMM 侧读物理地址、dump 页表，能快速证伪错误假设。
4. **先证伪再动手**：我一开始推断「DMA 冲刷页表」，靠 dump 页表 30 秒就推翻了——
   没有这一步会写一堆错方向的 cache 维护代码。
5. 测试脚本自身的 `/tmp` 文件属主、时序窗口、心跳干扰，都会伪装成「产品回归」，先看日志再改代码。

### 追加问题（同一轮）：真机多 USB 设备时抓到 tablet → 键盘没就绪

## 第十五轮（2026-10-24 晚）：退格键（Backspace）—— 帧缓冲控制台不吃 `\b` ✅

### 现象
用户真机反馈：「一般现在是能用，但是删除键你没做」——能打字，但退格删不掉。

### 根因（三层，只有第三层真缺）
1. HID 键码表：`0x2A Backspace → '\b'` —— **本来就有**（`usb_kbd.c` 的 `hid_map`）；
2. shell 行编辑：`if (c == '\b' || c == 127) { linelen--; uart_puts("\b \b"); }` —— **本来就有**；
3. **帧缓冲控制台**：`fb_draw_cp()` 只处理 `\n`/`\r`/`\t`，`\b`(0x08) 掉进「画字符」分支被画成 `?`，
   光标不左移、格子不擦 → 屏幕上完全看不出来删除。
   （串口终端本来就能吃 `\b`，所以只接串口时永远发现不了这个 bug。）

### 修法
- `kernel.c` 的 `fb_draw_cp()`：新增 `\b` 分支 —— 光标左移一格（`fb_x -= FONT_W`）并把该格像素抹黑；
  行首退格忽略（shell 不跨行退）。
- `usb_kbd.c` 的 `hid_map`：补 `0x4C Delete → 127`（shell 把 127 也当退格），
  让键盘上标着 Delete 的那个键也能删字（真正的前向删除需要插入点，暂不做，已在代码注释里写明）。
- `test_kbd.py`：新增退格用例 —— 打 `helz` → 退格 → `p` → 回车，
  断言出现命令清单（若退格无效命令会变成 `helzp`，不会执行）。`type_text` 增加 `\b → sendkey backspace`。

## 第十六轮（2026-10-25 早）：内核优化 —— 帧缓冲映射修正（滚动 70ms → 1.8ms）✅

> 背景：今早（07:00~07:55）有一轮「全面从内核优化」的工作（阶段 6②），但**没留痕**，
> 而且过程中在 NAS 上堆了多个 KVM 测试虚拟机，把 NAS 拖死过一次（用户 08:0x 反馈，NAS 于 07:57 重启）。
> 本轮先补齐取证，再修正其中一处方向性错误，并给所有测试脚本加宿主资源护栏。

### 一、今早那轮改了什么（对照 NAS `本体/` 昨晚版 diff 得出）
| 位置 | 改动 |
|---|---|
| 帧缓冲映射 | Device-nGnRE → **Normal-NC**（MAIR Attr2=0x44），并把对应 2MB 块改写 `PROT_FB_BLK` |
| 帧缓冲批量写 | `fb_clear_all`/`fb_scroll` 用 u64（2 像素）批量写，`fb_u64_ok` 守对齐与偶数跨度 |
| RAM 映射 | `l2_ram[1..63]`（128MB）→ `l2_ram[1..511]`（**整 1GB**），因为 UEFI 的 GOP 帧缓冲实测落在 0x4c430000 |
| 64 位 MMIO | 新增 `l0_table[1]` → `l1_hi[512]`，覆盖 0x8000000000 起 256GB 的 Device 映射 |
| 文件系统 | `fs_memset` 逐字节 → 8 字节批量（1MB 格式化少跑 100 万次循环） |
| 工具 | 新增 `bench` 命令（内核微基准）、`bench_boot.py`（启动计时）、`clean_qemu.py`（清遗留测试 VM） |

### 二、发现的方向性错误：NC 比 Device 好，但远不如 Cacheable
用 `bench` 在同一环境（KVM + ramfb，800×600）实测，同一块帧缓冲：

| 项目 | Normal-NC（今早） | 本轮 Normal-WB |
|---|---|---|
| fb 清屏 1 屏（纯写） | 447 µs（4 GB/s） | **~1.1 ms**（写已饱和，见注） |
| **fb 滚动一行（要读要写）** | **70 ms（25 MB/s）** | **1.8 ms（约 1 GB/s）→ 38×** |
| fb 画 1000 字符 | 485 µs | ~0.83 ms |

- **为什么滚动特别慢**：滚动要**读**帧缓冲。Non-Cacheable 下每个 8 字节读都直接怼 DRAM
  （约 365 ns/次），写却快得多 → 同一块内存「写 4 GB/s、读 25 MB/s」的怪现象。
- **排除「被宿主陷住」**：宿主 `kvm_mmio` tracepoint 在 bench 期间只有 3726 次退出，
  **落在 0x4x/0x5x（帧缓冲/RAM）段的 0 次** → 这 70ms 完全是 guest 自己烧的，不是 KVM 退出开销。
  （这也是「NAS 卡」的一个诱因：客人 100% 占一个核在搬像素。）

### 三、修法
1. `PROT_FB_BLK` 改成 **Normal-WB**（`PTE_ATTR_NORM`）—— QEMU/KVM 里 guest 的 cacheable 内存
   就是宿主的 cacheable 内存，ramfb 显示端读同一份物理内存、同一 cache 域，**天然一致**，
   不需要任何 `dc civac`。（真机若有真实扫描输出设备才需要 cache 维护——代码注释已写明。）
2. 顺手加 `fb_copy16`/`fb_zero16`（`ldp/stp` 16 字节），滚动/清屏/退格抹黑都走它。
3. 删掉没用上的 `fb_px2` 表（编译警告）。
4. **宿主护栏**（针对 NAS 被拖死）：
   - `probe_fb_boot.py`：可用内存 < 需求+150MB 直接拒绝；`/tmp/loongos_probe.lock` 单实例锁；
     默认 `-m 256 -smp 1`；`finally` 里 terminate→kill；硬超时。
   - `probe_bench_cost.py`：同样的内存/锁护栏。
   - 结论性数据：**一个空闲 guest 只吃 39MB RSS、0% CPU**（-m 192 实测）→ 卡死不是「跑一个 VM」造成的，
     是多个 512MB/2vCPU 测试 VM 叠加 + NAS 只有 2GB 内存/少核造成的。

### 五、教训
1. **映射属性要用数据选，不要凭直觉**：Device→NC 确实快了一个数量级，但 NC 仍是「逐次怼 DRAM」；
   在虚拟化环境里 **Cacheable 才是对的**（同一 cache 域）。
2. **优化前先量宿主侧**：`kvm_mmio` tracepoint 一秒就能区分「被宿主拖慢」和「guest 自己慢」。
3. **测试基础设施要自带资源护栏**：内存门槛 + 单实例锁 + 必杀 + 硬超时。
   小内存 NAS 上并发起多个 512MB/2vCPU 的 VM = 把宿主拖死。
4. 早前那轮改了代码却没留痕 → 只能靠 NAS 归档的旧版本 diff 才还原出来。**每轮必留痕。**

1. **UEFI 会优先从「已装过系统的硬盘」启动，不走 ISO**（真实坑）：

### 第二十四轮（2026-10-30）：POSIX 文件接口 + 第一个用它的用户程序 ✅

**目标（SSH 移植路线第③阶段的第一块）**：LoongOS 的 EL0 原来只有 2 个系统调用（write→串口、exit），
任何真实程序都跑不了。本轮加上 fd 表和文件系统调用，并用一个真正的程序验证。

### 做了什么

- **内核 `svc_dispatch` 扩到 6 个系统调用**：
  | nr | 名称 | 说明 |
  |---|---|---|
  | 0 | `write` | 两种形态：`write(ptr,len)`（老程序兼容，x0 落在用户区就当指针）/ `write(fd,buf,len)`（fd=1/2 → 串口） |
  | 1 | `exit` | 不变 |
  | 2 | `open(path,flags)` | 返回 fd；**打开时把整份文件读进内核缓冲**（每 fd 512 字节） |
  | 3 | `read(fd,buf,len)` | 按 fd 偏移拷出，返回字节数，0=EOF |
  | 4 | `close(fd)` | 释放槽位 |
  | 5 | `lseek(fd,off,whence)` | 0=SET / 1=CUR / 2=END，越界自动夹到 [0,len] |
- fd 表：`NFDS=6`（0/1/2 保留给标准输入输出），每 fd 一带 `ino/off/len` 的 512 字节缓冲。
- **指针安全**：`u_strcpy()` 先把用户指针卡在 `[USER_BASE, USER_END)`，再在限制长度内找 NUL；越界一律返回 `-1`，不复刻「内核替用户改参数」的老毛病。
- 新用户程序 **`user/cat.c` → `/bin/cat`**：`open → read（512 循环）→ write(1,...) → close`，全在 EL0 跑。
- `user/user.h` 增加 `sys_call3` 与 `u_open/u_read/u_close/u_seek/u_write` 薄封装。

## 第二十五轮（2026-10-30）：用户区独立 2MB + argv 传递（fork 的地基）✅（含 1 项未解异常）

**背景**：为 SSH 路线的 fork/exec 做准备。原布局里用户程序挤在内核那个 2MB 块的顶部 64KB
（`USER_BASE=0x401F0000`），BSS 已到 `0x401ED010`，只剩 ~12KB —— fork 的地址空间根本无处安放。

### 做了什么

1. **用户区独立成整整 2MB**：`USER_BASE 0x401F0000 → 0x40200000`，`USER_END 0x40400000`，
   新增独立 L3 表 `l3_user`，`fill_l3` 升级成 `fill_pt`（按地址自动选 `l3_kern` / `l3_user`）。
   以后每个进程换自己的 `l3_user` 副本即可切换地址空间 —— 这就是 fork 的入口。
   ⚠️ **踩坑**：`l2_ram[1] = l3_user` 必须写在「批量填 2MB 大页」那个循环**之后**，
   否则被覆盖回大页（大页带 UXN）→ 用户代码一取指就是 **2 级权限故障**（ESR IFSC=0x0E，FAR=入口地址）。
2. **argv 传递**：内核装载时把 `argc / argv[] / 字符串池` 写到固定 VA `0x403FEE00`
   （`USER_END - 栈保留 4KB - 512`），`user.h` 提供 `u_argc()` / `u_argv(i)`；
   `run <路径> [参数…]` 支持带参数；新程序 `/bin/args` 打印全部参数。

## 第二十六轮（2026-10-31）：SMP 启动 + per-CPU 状态 + 控制台锁 ✅

**目标**：用户要求「适配一下多核」。按 Linux 的四层模型拆解，本轮完成前两层。

### 做了什么

**1. SMP 启动（`smp.c`，新文件）**
- PSCI `CPU_ON`（`smc #0`，不支持则回退 `hvc #0`）拉起 1..3 号核，返回码 0/-3 视为成功
- 从核入口 `smp_secondary_entry`（汇编）：读 `MPIDR_EL1.aff0` 选自己的 4KB 栈 → 装 CPU0 保存的
  `TTBR0/TCR/MAIR/VBAR` → `tlsc vmalle1` 清 TLB → 置 `SCTLR` 的 M/C/I 开 MMU 与缓存 → 跳 C
- 从核只跑计数循环（不碰 fs/UART，避免竞态）——先证明「核真的活了」

**2. per-CPU 私有状态（Linux `this_cpu()` 的简化版）**
- `struct percpu { cpu_id, tick, irq_depth, online, stack_top }`，每核一块
- 用 **`TPIDR_EL1`** 指向本核那块（aarch64 上每核独立的寄存器，天然不共享）
- `smp_tick_inc()`：手写 `ldxr/stxr` 原子自增（⚠️ **cortex-a57 没有 LSE 指令**，`__atomic_*` 会去调
  libgcc 的 `__aarch64_ldadd8_relax`/`__aarch64_cas4_acq`，而我们是 `-nostdlib`，链接必炸）

**3. 控制台自旋锁**
- `spin_lock/spin_unlock`（`ldaxr/stxr` + `stlr` + `yield`），`uart_putc` 只锁「写硬件」那一小段
- ⚠️ **关键坑**：开机早期 MMU 未开，内存是 **Device 属性**，`ldaxr/stxr` 在 Device 内存上不可用
  → 第一次上机直接黑屏卡死。修法：`smp_locks_on` 开关，MMU 打开后才真正上锁。

按依赖顺序定位并修复的根因（每个都单独会致失败）：

| # | 缺陷 | 权威依据 | 修法 |
|---|---|---|---|
| 1 | 队列内存用 `union` 叠放，除 `asq@0` 外 `acq/iosq/iocq/dbuf` 全不 4KB 对齐 | `nvme_start_ctrl()` 的 `asq & (page_size-1)` / `acq & ...` 直接 return -1 → CFS=1 | 改 U-Boot 式「每队列独占整页」：`.nvmedma` 段 6×4KB，按 `NV_*_OFF` 切开；加 5 区页对齐自检 |
| 2 | CC 的 `IOSQES/IOCQES` 整体左移 4 位（`0x04600001`） | QEMU `enum NvmeCc`：`IOSQES_SHIFT=16`、`IOCQES_SHIFT=20`；`nvme_create_cq()` 校验 `iosqes==6 && iocqes==4` | 宏化位域，正确值 `0x00460001` |
| 3 | CQE 相位/状态读 `c[0]`（DW0=result） | QEMU `NvmeCqe`：`status` 在 DW3 高 16 位；`ctrl.c` 写 `(status<<1)\|phase` | 改读 `c[3]`，相位 `bit16`、SC `bit[24:17]`、SCT `bit[26:25]` |
| 4 | Identify 数据用大端 `be32()` | QEMU `id->nn = cpu_to_le32(...)`；Linux `le*_to_cpu` | 新增 `le32/le64` |
| 5 | NN 偏移 / FLBAS / LBADS 全错 | NN@516；FLBAS@26；LBAF@128 每项 4B，DS 是第 3 字节 | 逐项改正 |
| 6 | **SQ 门铃写旧 tail** | U-Boot `++tail; writel(tail, q_db)`；QEMU 靠 `new_tail != sq->tail` 取命令 | 改写递增后的 `aq_sq_tail / io_sq_tail`。这是「控制器就绪但 Identify 超时」的直接原因 |
| 7 | 缓存维护只做 1 次 `dc civac/ivac`（仅 64B） | U-Boot `invalidate_dcache_range(start, stop)` | `nv_clean_buf/nv_inv_buf` 按 cacheline 遍历整段 4KB |

`test_nvme_install.py` / `test_stage5b_elf.py` 全挂。

解法：**ring 加来源标记 `ring_src[]`**（0=UART / 1=KBD），桌面主循环

配套「屏幕所有权」闸：桌面接管期间 `uart_putc` 不再把日志镜像到帧缓冲

### 三、踩到并修掉的坑（本轮核心技术点）

1. **裸 ELF 启动不能挂 pflash**：测试脚本同时给 `-drive pflash(AAVMF)` 和 `-kernel kernel.elf`，

3. **【真 bug】tablet + mouse 共存时按钮位被覆盖**（本轮最关键）：
   - 现象：`test_desktop_p2.py` 7/8，只有拖拽失败；`DESKTOP_MOUSE_DEBUG` 逐帧打印显示
     坐标正常变化（x 299→455）但 `btn` 恒 0、`drag` 恒 -1。
   - 对照实验：去掉 `usb-mouse` 只留 tablet → `btn=1`、`drag=1`、窗口拖动差异 0.42，全好。
   - 根因：QEMU `qemu_input_event_send_impl()` 每个事件只发给**一个** handler
     （`qemu_input_find_handler` 返回首个 mask 匹配者）：`ABS` 只能给 tablet，`BTN` 则给
     相对鼠标。于是「按下」由 mouse 报 btn=1，紧随的「移动」由 tablet 报 btn=0 ——
     原 `mouse_feed_*` 里 `G_mbtn = btn & 7` 直接覆盖，把按下位冲掉。
   - 修法：`G_btn_abs` / `G_btn_rel` 两个来源各存一份，`G_mbtn = G_btn_abs | G_btn_rel`
     按位或合并；任一设备按住即视为按住，两者都松开才清零（QEMU 的 down/up 成对发给同一设备）。
   - 附带确认坐标仍可「谁最后报谁生效」：相对鼠标收到的是 REL 事件、tablet 收到 ABS，
     两者不冲突；真机上谁动谁报。
4. **QMP `input-send-event` 的 device 参数是 QOM 设备名**而非 handler 名
   （传 `"QEMU HID Tablet"` 报 `DeviceNotFound`）；不指定时广播，故测试用「每批同时带
   abs 坐标 + btn 状态」的完整状态注入，避免只发 btn 时 tablet 该帧坐标被当成 (0,0)。
5. 两个编译告警：`desktop.c` 的 `G_mbtn` 未使用（删）、`btn_visible` 未使用
   （把窗口内按钮命中判断改成调用它，语义一致）。

## 第二十七轮（2026-11-08）：真机反馈「鼠标固定偏移 + 装不上」定位与修复 ✅

### 一、用户反馈（原话）

> 「每次打开的时候，我的鼠标和真实的鼠标都会有一定的偏差，但这个偏差又是固定的。」
> 「这个系统怎么装不上去？是哪里有问题吗？」
> 追问确认：偏差是**始终差固定一段像素**（不是比例缩放）；安装是 **`install yes` / `scsi` 检测不到硬盘**。

### 二、排查过程（先证伪，再定位）

1. **鼠标映射链逐段核对 QEMU 8.2.2 源码**：
   - `hw/usb/dev-hid.c` 的 tablet 报告描述符：6 字节、X/Y 各 16 位、Logical Maximum `0x7fff`；
     `hw/input/hid.c` 的 `hid_pointer_poll()` 布局为 `buttons, x_lo, x_hi, y_lo, y_hi, wheel`
     → 驱动 `pointer_report()` 解析**正确**。
   - `ui/input.c` 的 `qemu_input_queue_abs()` 会用 `qemu_input_scale_axis(value, min_in,
     max_in, INPUT_EVENT_ABS_MIN, INPUT_EVENT_ABS_MAX)` 把 VNC 的 `0..屏宽` **归一化到 0..32767**
     → 内核 `ax * (fb_w-1)/32767` **正确**。
   - `desktop.c` 窗口布局全部走 `gfx_width()/gfx_height()`，无硬编码 800×600；
     `draw_cursor()` 与 `handle_press()` 用同一组 `G_mx/G_my` → 内核内部**不存在两套坐标**。
   - 结论：固定常量偏移来自**客户端侧**（网页 VNC 画布留白 / 缩放没扣），内核改不了客户端，
     但可以做补偿；P2 测试用 QMP 注入坐标，从没覆盖过「UEFI + 网页 VNC」这条真实链路。
2. **磁盘用真机同构拓扑实测复现**（`/tmp/repro_realvm.py`）：
   `virt-7.2` 风格、`-smp 2`、GICv3、AAVMF 从 ISO 启动、4 个 pcie-root-port、
   virtio-scsi 挂桥后 bus4、CD(raw ISO) + 硬盘(qcow2) 同控制器、ramfb + 三 USB 输入。
   结果：`[stub] GOP fb ... 800x600` → `[scsi] 扫描总线数=5` → `找到设备 bus=4 dev=0 fn=0`
   → `候选 target=1 lun=0 类型=0（硬盘）` → `[disk] virtio-scsi 就绪，容量 8 MB`。
   **磁盘驱动本身工作正常**，多级桥 BFS 与 CD/HDD 区分都对。
3. **定位「装不上」主因**：真机 VM 的域配置里
   `<source file='/vol1/1000/项目/loongos/iso/自研内核ISO/loongos-kvmfix.iso'/>`，

## 第二十八轮（2026-11-09）：真机反馈「鼠标根本滑不动，点一下才知道位置」修复 ✅

### 一、用户反馈（原话）

> 「鼠标根本滑动不了，要点击一下才能知道鼠标的位置。」

这是继上一轮「固定偏移」之后更基础的新现象：光标**不实时跟随移动**。上一轮把问题
归因为客户端常量偏移并加了 `mousecal` 补偿，同时引入的「绝对优先」时间窗口反而
造成了这次回归。

### 二、复现（先补测试盲区）

新增 `test_mousemove.py`：QEMU + ramfb + xhci + tablet/mouse/kbd，用 QMP
`input-send-event` 分阶段注入，**全程不发按键**：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| 1 单次绝对移动 (400,300)→(200,150) | ✓ 跟随 (0.033/0.034) | ✓ 跟随 |
| 2 连续 8 步绝对轨迹 | ✓ 跟随 (0.063/0.033) | ✓ 跟随 |
| 3 相对移动 (-70,-50) | ✗ **差异 0.000，完全不动** | ✓ 跟随 (0.033/0.063) |
| 4 坐标不变只点击 | 旧位置框 0.184（整屏重画才现形） | 0.000 |

关键点：既有 `test_desktop_p2.py` / `test_mousecal.py` 的 `click()` 都自带一次
`abs_move(x,y)`，所以即使「纯移动不刷新」也照样全绿——这是从未被覆盖的测试盲区。

### 三、根因

`kernel.c` 的 `mouse_feed_rel()`（P2.1 加入）：

```c
if (!G_abs_seen || tick - G_abs_tick > 20) {   /* 20 ticks @10Hz = 2 秒 */
    G_mx += dx; G_my += dy;
}
```

- `tick` 由 ARM Generic Timer 的 10Hz 中断递增（`handle_irq` 里 `tick++`）。
- 平板每次绝对报告都刷新 `G_abs_tick`；真机网页 VNC 若走**相对模式**，平板只在
  开机报过一次，但内核仍把「近期有绝对报告」当作平板在场的依据。
- 结果：相对鼠标的所有位移被 2 秒窗口长期吞掉，`G_mx/G_my` 不更新，光标画在旧
  位置不动；只有点击触发 `handle_press()` → `gfx_damage(full_screen())` 整屏重画时，
  光标才被画出来一次 —— 正是用户描述的「点一下才知道位置」。

这个窗口基于一个错误假设：以为 tablet + mouse 会「轮流覆盖坐标」。核对 QEMU 8.2.2
`ui/input.c` / `hw/input/hid.c` 与 P2 实测记录后确认，绝对模式下相对鼠标**只收 BTN
事件、dx/dy 恒为 0**，根本不会覆盖平板坐标，无需按时间猜来源。

### 四、改动清单

| 文件 | 改动 |
|---|---|
| `kernel.c` | `mouse_feed_rel()` 去掉 `tick` 时间窗口：非零相对增量一律累加，`dx==0 && dy==0` 的纯按钮/滚轮报告不动坐标；删除 `G_abs_seen` / `G_abs_tick` 与多余的 `extern volatile u64 tick`；新增 `G_abs_cnt` / `G_rel_cnt` 计数，`cmd_mousecal()` 查询时打印「指针报告数 绝对=N 相对=M」，真机可直接判断 VNC 模式 |
| `test_mousemove.py`（新） | 四阶段「只移动不点击」回归，绝对/相对全覆盖 |
| 文档 | `LOONGOS_DESKTOP_TODO.md` 增 P2.2 并把 P2.1「坐标源互斥」标注撤销；README 补 P2.2、测试清单、诚实边界 |

`mouse_feed_abs()` 的映射与 `mousecal` 偏移补偿保持不变（VNC 相对模式下内核光标
从屏幕中心累加位移，与客户端物理光标起点不同，`mousecal` 仍可补偿常量差）。

### 五、验证

- 编译零警告，四项 BSS 守卫通过，`__nvmedma_end=0x4020e000 < USER_BASE=0x40210000`，余量 8 KB。
- `test_mousemove.py`：1/2/3 全 ✓，只点击阶段 0.000。
- 全套回归：`test_mousecal.py` / `test_desktop_p2.py` / `test_nvme_install.py` /
  `test_uefi.sh` 5 拓扑 / `test_stage5b_elf.py`。
- `kernel.elf` md5 `072bbda9a838223050feacc75b32e977`；ISO 五方 md5 一致（唯一 md5 个数 = 1）。

### 六、给用户的动作项

1. 换用重建后的最新 `loongos.iso`（v1.1.2），鼠标应可直接滑动，不再需要点击定位。
2. 若仍有固定偏差：图形终端敲 `mousecal` 看「指针报告数」——绝对多说明 VNC 走平板、

## 第二十九轮（2026-11-10）：ARM 内核结构性优化 —— 为后续新功能铺路，功能零变化 ✅

### 一、用户需求与硬约束

> 「先对 arm 内核进行优化。为后续新功能的添加做铺垫。对于现在功能不变的前提下。」

关键词是**「铺垫」+「功能不变」**：不新增可见功能，只把内核内部整理成能安全继续加东西的形状；
且「不变」不能靠嘴说，必须拿出可复核的硬证据。因此本轮先造两把尺子，再分四阶段推进，
每阶段结束时都用尺子量一遍。

### 二、两把尺子（基线固化）

| 尺子 | 内容 | 稳定性 |
| --- | --- | --- |
| 构建可复现性 | 优化前 `kernel.elf` md5 `072bbda9a838223050feacc75b32e977`；`iso/loongos.iso` md5 `0040a584…` | 从 git HEAD 检出到临时目录重编译，md5 逐字节复现 |
| 行为黄金基线 `golden_behavior.txt` | QEMU `-machine virt,gic-version=2 -cpu cortex-a57` 下完整启动日志 + 29 条确定性命令输出，规范化地址 / tick / 心跳后逐字比对，232 行 / 7168 B | 连续两次采集一致 |

`test_behavior.py` 用 `-chardev socket,...,server=on,wait=on -serial chardev:s0` 抓完整启动日志
（`wait=on` 是关键：否则客户端连上前的启动日志会被 chardev 丢弃，`=== BOOT ===` 段为空）。
规范化踩过两个坑：① `cpu` 命令打印 2~3 位 tick，加 `RE_TICK` 单独处理；② 曾误用旧的

### 三、阶段一：零行为变化的结构解耦

**问题**：100+ 个跨模块 `extern` 声明散落在各 `.c` 顶部，重复、类型漂移

甚至有幽灵声明 `kputhex2`；`build.sh` 的 rm 清单 / 编译行 / 链接行各写一份 20 个文件名，
新增驱动要改 3 处，漏一处就混进陈旧 `.o` 或链接缺符号。

**改动**：

| 文件 | 改动 |
| --- | --- |
| `loongos.h`（新） | 跨模块声明唯一事实来源，自带 `u8/u16/u32/u64` 类型 guard；统一控制台 / 输入 / 块设备 / PCI / fs / 网络 / TCP / rng / SMP / tick / 链接器符号 / 内嵌 blob；`cnt_read/cnt_freq` 因内核构建下是 `static inline` 而不纳入（仅 `NET_NO_CNT` 宿主测试保留 extern） |

### 四、阶段二：块设备统一抽象层 blkdev

**问题**：`virtio_blk.c` 名义只管 virtio-blk，实际 `vb_present/vb_capacity_bytes/
vb_capacity_sectors/vb_read/vb_write` 五个函数各硬编码一段
`if (!vb_ok) { if (vs_present()) ...; if (nv_present()) ...; }`；`kernel.c` 启动链又单独
写了一遍 `vb_init → vs_init → nv_init` 优先级。新增一个驱动要同时改 7 处，漏一处就
「认得到盘但读不了」或「读的是错的盘」。

**改动**：

| 文件 | 改动 |
| --- | --- |
| `blkdev.h/.c`（新） | `struct blkdev_ops`（init/present/capacity_*/read/write）+ `blk_drivers[]` 唯一优先级表 + `blk_probe_all()` / `blk_find()` / `blk_*` 统一门面；`vb_*` 保留为兼容门面，既有调用点一行不改 |
| `virtio_blk.c` | 拆掉全系统门面，导出私有 `vb_dev_*` 与 `const struct blkdev_ops vb_ops`；**legacy 成功时 `vb_ok` 仍为 0，不"顺手修"历史语义** |
| `virtio_scsi.c` / `nvme.c` | 各导出 `vs_ops` / `nv_ops` |
| `kernel.c` | 启动探测链改用 `blk_probe_all()`；`disk_kind` 用 `blk_active` 索引取名（不用 `blk_name()`，因 legacy 下 `vb_ok=0` 会让 `present()` 返回 false，与历史打印不符）；`cmd_disks` 的「后写覆盖」语义原样保留 |

为严格遵守「功能不变」，抽象保留三条历史语义：优先级 virtio-blk > virtio-scsi > nvme；
virtio-blk 的 capacity_bytes 在 legacy 下用 `vbl_capacity_bytes()`；探测遇第一个 init 成功即停。

**验收**：行为基线逐字一致；`kernel.elf` md5 变为 `c2a7f64e…`，把 `blk_init_rc` 显式初始化
移入 `.data` 后为 `bcb6e939…`；NVMe 装盘 / UEFI 5 拓扑 / 桌面 P2 8/8 / EL0 33/33 全通过。

### 五、阶段三：BSS 余量诊断 + 空间预算守卫（本轮技术重点）

**现象**：阶段二后守卫报余量从 **8 KB 掉到 4 KB**：
`__bss_end 0x402075c0→0x402085c0`、`__nvmedma_end 0x4020e000→0x4020f000`，
`.bss` size 正好 `+0x1000`。

**精确根因**（逐符号比对两份 ELF 的 `.bss`，非猜测）：

```
优化前:  l_ring @0x401e2000 (size 0x2000, 终点 0x401e4000)
         0x401e4000 vs_desc      ← 4KB 对齐缓冲，正好落在边界，零填充
         vs_ok 藏在 0x401e6124（vs_avail 之后的空隙）
阶段二:  0x401e4000 vs_ok (4B)  ← 被重排到组首，占了边界槽
         0x401e5000 vs_desc      ← 被迫对齐到下一页，凭空多 4092B 填充
         → 整条 4KB 对齐链后移一页，_stack_bottom/__bss_end/.nvmedma 全部 +0x1000
```

两条结论：① 这 4 KB **不是泄漏、也与新增 `.data` 无关**（`.bss_start` 两份都是
`0x400b6000` 未变），是 `.bss` 内对齐碎片对符号顺序敏感；② 4 KB 余量仍为正、被硬守卫
覆盖、对功能零影响。**因此没有为了「把数字拉回 8 KB」去改链接布局或削减 32 KB 内核栈**
——那类改动风险大于收益，且与「功能不变」相悖。

**真正的修复**：让余量变化再也不会悄悄发生。`build.sh` 守卫从「四项硬检查」升级为：

- 分段预算表（`.text/.rodata/.data/.bss/.nvmedma` 各自大小 + DMA 对齐浪费 + 上界余量）；
- 三级阈值（≥6KB 充裕 / 4~6KB 关注 / 0~4KB 偏紧 / ≤0 禁止构建）；
- `bss_budget.txt` 团队基线 + 「相对上次 ±N B」delta，构建失败时 awk 在写基线前就 `exit 1`；
- 四项硬检查语义不变，越界一律 fail fast。

**踩到并修掉的坑**：awk 脚本里曾用 `RS` 当 `__rodata_start` 变量，**覆盖了 awk 内置的
记录分隔符 `RS`**，导致 `getline < bf` 把整个基线文件当成一条记录，`^margin_bytes=`
匹配不上、delta 静默丢失（表面看构建全绿，实际少了一条预警）。改用 `ROS/ROE` 并留注释。

**越界拦截实证**：临时副本给 `blkdev.c` 追加 20 KB 未初始化静态数组 →
预算表显示 `.bss 1373.4 KB`、`余量 -16.0 KB`、`X __nvmedma_end 已顶到/越过 USER_BASE`、
`build rc=1`。「新增功能不越界」不再是一句口号。

完整布局、根因链、扩容三方案（独立段 / 上移 USER_BASE / 不推荐的削栈）见
[内核空间预算与扩容指引.md](内核空间预算与扩容指引.md)。

五方 md5 一致（ISO9660 树 / payload.img / esp.img / 源码 `kernel.elf` 均为 `bcb6e939…`，
唯一 md5 个数 = 1）；两份 ISO 副本 + 两个 md5 文件已统一。

### 七、诚实的边界

- 本轮**没有新增任何用户可见功能**，全部是内部结构优化；「功能不变」由 md5 逐字节 +
  行为基线逐字 + 9/9 回归共同支撑。
- 上界余量现为 **4 KB**（不是 8 KB），根因是链接对齐碎片、非泄漏；预算守卫会在它继续

- `kernel.elf` 相对优化前已变化（`072bbda9… → bcb6e939…`），这是阶段二抽象层的预期结果；
  阶段一曾做到逐字节不变。
- 4 KB 跳变说明 `.bss` 布局对符号顺序仍敏感；彻底治本需把 `aligned(4096)` 缓冲收进
  独立段（见扩容指引方案 1），属下一次专门的布局重构，不夹在本轮「功能不变」里做。

## 第三十轮（2026-11-10）：桌面手感优化 P3 —— 输入即时化 / 边沿事件 / 白色闪烁光标 ✅

用户反馈（真机 ARM 桌面）：「鼠标滑动不跟手、点击像点不准、键盘输入有延迟；想要一个跟 Linux 差不多的、显示正在输入的闪烁白点」。目标是像 Windows / 带 GUI 的 Linux 那样「滑动就是滑动、点击就是点击」。

### 一、根因：主循环 `wfi` 让输入排队等 100ms

`desktop.c` 的 `desktop_run()` 每轮 `__asm__("wfi")`。核查中断使能：整机**只使能 UART(33) 与 TIMER(30) 两个 IRQ**，xHCI 是纯轮询设备、不产生中断。于是 `wfi` 只能被 **10Hz timer（100ms 一拍）** 或串口字符唤醒：

- 鼠标位移、键盘按键全要排队等到下一个 100ms 拍子才被 `usb_kbd_poll()` 收割、才 `gfx_present()` → 「不跟手 + 输入延迟」的共同根因；
- 画面只有 10fps → 任何闪烁动画根本做不了。

另外 `poll_mouse()` 用「合并按钮状态快照」与 `G_mprev` 比较得 pressed/released：一拍内若「按下+松开」都发生，快照只看到最终态，中间边沿被吞 → 快速点击 / 短拖拽偶发失灵。

### 二、三处改动

1. **P3.1 主循环输入即时化**：去掉 `wfi`，改连续 `usb_kbd_poll()` + ring 消费 + `poll_mouse()`；有输入立即 `gfx_present()`。空闲用 `cntpct_el0`/`cntfrq_el0` 硬件计数器做 **60fps 帧节流**（驱动闪烁与时钟）。原挂在 wfi 节拍上的 10Hz 任务（`smp_tick_inc` / `net_poll` / 安装向导超时 / 时钟刷新）改成按 `tick` 变化执行，频率与语义不变。循环末尾用 `yield` hint，不睡眠。串口让位与 `Ctrl+Shift+F1` 退出保持原样。
2. **P3.2 按钮边沿事件队列**：`kernel.c` 新增 32 槽环形 `G_mbtn_q[]`，`mouse_feed_rel/abs()` 在合并按钮状态每次变化时 `mbtn_push()`；导出 `mouse_pop_btn()`。`desktop.c` 的 `poll_mouse()` 逐事件分派 pressed/released，坐标仍读最新 `G_mx/G_my`（滑动连续不受影响）。
3. **P3.3 白色闪烁插入光标**：`gfxterm.c` 从 8×16 青绿实心恒亮方块改成白色闪烁方块——打字 `G_key_kick` 重置亮相位（`GT_BLINK_HOLD_MS=500` 常亮），之后 `GT_BLINK_HALF_MS=500` 亮/灭翻转；相位切换只脏输入行 22px（`G_inrect`），不重绘 64 行历史。在**共用绘图层** `gfx_draw.h` 加架构中立的 `gfx_draw_caret()`，X86 `desktop_x86.c` 用 PIT `g_ticks`(100Hz) 驱动同一 helper，两架构手感一致。

### 三、启动期挂死事故：`.bss` 地址漂移引爆 fw_cfg DMA（本轮最硬的坑）

全套回归从 9/9 掉到 **6/9**，三个桌面测试全「桌面未就绪」，串口日志只停在 `[probe] A pl011 ok`。这是本轮改动引入的真回归，逐层定位：

1. **对照实验**：从 git HEAD(v1.1.3) 检出编译一份 P3 前内核，图形拓扑正常进桌面 → 确认本轮引入。
2. **二分**（从对照版逐个加入 P3 文件）：C0~C3（加 `gfx_draw.h`/`loongos.h`/`gfxterm.*`）都正常，**C4（仅加 `kernel.c`）立刻挂死** → 锁定 `kernel.c`。
3. **排除内存越界**：对比三份 ELF 的段边界、`__bss_end`、`_stack_top`、`__nvmedma_end`、4096 对齐锚点、上界余量（4 KB）——四份几乎完全一致，`__bss_end` 只差 32 B，守卫全部通过，**不是越界/布局跳变**。
4. **逐笔插桩**：在 `fwc_ramfb_setup()` 打点，目录读取正常（n=11、找到 `etc/ramfb` sel=0x25 sz=28）、cfg 构造完成，一进 `fwc_dma_write()` 就卡住；再在 `fwc_dma_write()` 四次 MMIO 写之间逐笔打点，卡在 **D5 之后、D6 之前**（第四笔 `*(FWC_DMA+4)=lo` 正确触发 ramfb DMA 之后没回来）。
5. **决定性对照**：
   - E1（删掉多余的第一遍 bswap 触发、只发正确 DMA 一次）→ **仍挂死**；
   - E2（把 `fwc_cfg_buf`/`fwc_dma_desc` 显式初始化放 `.data`）→ **恢复正常**。

   `kernel.c` 新增的 136 B 按钮队列变量把这两个 `.bss` 静态缓冲从 `0x400b8778/0x400b8798` 推到 `0x400b8808/0x400b8828`；QEMU fw_cfg DMA 对描述符/数据缓冲的**绝对地址敏感**，第四笔触发后 guest 挂住。与逻辑、越界、对齐、余量全无关，是潜伏已久的启动期隐患，被 `.bss` 增长引爆。

**修复**：`fwc_cfg_buf[28]`/`fwc_dma_desc[16]` 加 `= {1}` 显式初始化落 `.data`，地址与 `.bss` 增长彻底解耦；`fwc_dma_write()` 会写满 28B/16B 全覆盖，初值无副作用。**并在 `build.sh` 加「段归属守卫」**：两个符号的 nm 类型必须是 `d/D`（.data）或 `r/R`，落回 `b/B`（.bss）立即 fail fast，附带 2026-11-10 事故注释。正反映证：修复版放行、改回 `.bss` 的副本被拦（rc=1）。

### 四、测试方法论：QMP 通道测不了内核微秒级延迟

新增 `test_desktop_p3.py` 做 P3 前/后量化对照，一度得到忽高忽低的数字，逐个查清：

- **「发完立刻截屏」**测 T1 即时性：P3 后是 60fps 局部脏矩形重绘，`screendump` 会抓到**半帧/窗口撕裂**（实测截图可见窗口被截断），`dn` 呈 `0→0.036→0.504→1.000` 递增，是撕裂不是光标不即时。
- **QMP `sendkey` 注入自带 60ms~数百 ms 抖动**：诊断脚本 `diag_key.py` 实测发 5 键后 `0ms→0.000`、`60ms→0.045` 才稳定；P3 前内核同样如此 → 键盘回显两版功能上都正常，`0.000` 只是截屏抓早了。
- **结论**：把判据分成两类——【功能不回归】T1 纯移动跟随 / T3 键盘回显用稳定等待法（两版都 PASS）；【P3 改善】T2 极短快速点击、T4 白色光标闪烁用确定性二值判据。

**最终稳定对照**：

| 判据 | P3 前 v1.1.3 | P3 后 | 说明 |
| --- | --- | --- | --- |
| T1 纯移动跟随 | 5/5 PASS | 5/5 PASS | 功能不回归 |
| T3 键盘回显 | 0.035 | 0.033 | 功能不回归 |
| **T2 极短快速点击** | 0.006 边沿被吞 | **0.936 菜单打开** | 旧版 100ms 快照吞掉同拍 按下+松开；新版边沿队列不丢 → **输入即时化最硬的确定性证据** |
| **T4 白色光标闪烁** | 0.000 恒亮 | **0.267 在闪** | 同时证明帧循环从 10Hz 提到 60Hz（旧版根本闪不起来） |

键鼠走同一 `usb_kbd_poll()` 收割路径与同一主循环，T2 的结论对键盘同样成立。微秒级延迟本身无法用 QMP 通道测量，架构层根因与修复写在 `desktop.c` 主循环注释里。

X86 同步：`build_x86.sh` 只产 `kernel_x86.elf`、不重建 ISO，闪烁专项初测 FAIL（跑的是 11-09 旧 ISO）。执行 `build_iso_x86.sh` 重建（内嵌内核 md5 `addc2026…` 与源码一致）后：`test_x86_blink.py` 相邻帧差异 **0.205**（在闪 PASS）、`test_x86.py` 端到端 **6/6 ALL PASS**。顺带修 `test_x86.py` 第 4/5 项判据：P3.3 把输入条改成深色底后，旧「深色像素增加」判据会因白字白光标反而下降（before=5482 after=5212 误报），改统计**白色像素增加**（before=18 after=288 / typed=288 long=988）。

## 第三十一轮（2026-11-11）：系统资源调配优化 R —— CPU 50%→0.6% ✅

> ⚠️ **本轮「三、内存」小节的结论已被第三十二轮推翻**：当时把 fw_cfg DMA 缓冲
> 钉到固定物理地址 `0x4007E000`，用「进桌面」当成功判据误判为成功，实际导致
> ramfb 黑屏。最终方案是静态数组 `.data` + `test_framebuffer.py` 真实画面判据。
> 下面保留原始记录以完整呈现排障脉络，正确结论见第三十二轮。

用户诉求：「全面优化系统资源调配」。本轮把 CPU、时钟节拍、内存布局三类资源一起整理，
**不改任何用户可见功能**（行为黄金基线逐字一致 + 全套回归）。完整设计见
[系统资源调配.md](系统资源调配.md)。

### 一、基线：一次实测暴露的架构问题

新增 `test_idle_cpu.py`（宿主侧 `/proc/<qemu-pid>/task/*/stat` jiffies，guest 无法伪造）：
桌面静置 8 秒 **CPU=4.00s/8.00s = 50.0%**。不是 100% 而是 50%，恰好解释老架构——
10Hz 抢占轮转让 task0(桌面忙等) 与 task1(worker `wfi`) 各占 100ms 时间片，一半烧满一半睡。
P3 为修输入延迟去掉了 `wfi`，代价就是空闲占满一核；而 `wfi` 只能被 10Hz timer/UART
唤醒（xHCI 无 IRQ），睡回去就退回 100ms 延迟 —— 看似不可兼得。

### 二、CPU / 时钟：硬件唤醒频率 与 软件 `tick` 解耦

`tick` 被 fs mtime(`tick/10`)、EL0 看门狗(300ticks=30s)、task1 心跳、抢占轮转、
桌面时钟/10 秒超时写死成 10Hz，不能提频。设计：

1. `timer_set_wake_hz()` 让硬件 timer 独立跑 120~1000Hz，只负责把 CPU 从 `wfi` 叫醒去
   `usb_kbd_poll()`；桌面态 `g_desktop_active=1` 抑制 `task_switch`（否则 `wfi` 醒来被切
   到 worker 卡 100ms，正是 P3 当初去掉 `wfi` 的深层原因）。
2. `tick` 由 `cntpct_el0` 真实经过的 **cycle** 结算（累计差值，够 `freq/10` 补一个 tick，
   一次 IRQ 可补多拍），与唤醒频率彻底无关；串口 shell 下仍与原版逐字节等价。
3. 桌面自适应调频：ACTIVE 1000Hz / IDLE 250Hz / DEEP 120Hz；**有输入全速不睡**（保 P3
   跟手感），空闲 `wfi` 真睡，任意输入立刻回 ACTIVE。

**三个实测踩坑（都靠 `test_resource_live.py` 用 QMP 读 guest 内存抓出来，不是猜的）：**

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 3s 只涨 20 tick（应 30） | 「每 N 次 IRQ 才 tick++」数 IRQ 分频，但 QEMU TCG 下设定 1000Hz 实际只触发 ~558Hz | 改用 cycle 结算，实测 3.2s 精确 +32 |
| 2 | 3s 后仍 250Hz 不降到 120 | `cntpct_el0` 虚拟时间 ≠ 墙钟，`idle_ms` 被低估 | 空闲计时改用 `tick`（恒 10Hz） |
| 3 | 仍卡 250Hz | 闪烁光标/时钟/超时都会置 `input`，不断刷新空闲起点 | 独立 `real_input`，只认真实键鼠事件 |

结果：**50.0% → 1.9%（首版 wfi）→ 0.6%（DEEP 档生效），约 83 倍**。在线验证 ALL PASS：
桌面态=1、TIMER IRQ 与 wfi 命中持续增长（证明**省电不是靠冻住画面**）、自适应降 120Hz、
tick 恒 10Hz、DEEP 段 IRQ 频率显著低于 ACTIVE 段。

### 三、内存：勘误上一轮，根治「加功能就挂死」

上一轮（第三十轮）把图形启动挂死归因为「fw_cfg DMA 缓冲必须留在 `.data`」。本轮用
**7 组对照实验**纠正：

- V1（`.rodata`+128B）稳定 4/4 HANG，V0 稳定 2/2 进桌面 —— 不是 flaky；
- padding 扫描：`.data` **内部**加变量不推移缓冲地址；
- **密集地址扫描**画出 QEMU fw_cfg DMA **危险窗口**：`0x400ae4f0/500/510` HANG，
  `0x400ae480~4e0` 与 `0x400ae520~5e0` 安全；
- **逐符号 ELF 对比** YES(D1,缓冲 0x400ae590) vs HANG(n128,0x400ae500)：
  `.bss`/栈/`.nvmedma`/所有段边界**完全相同**，唯一差异就是 `.data` 起点 + 两个缓冲地址；
- `.data` 钉到 +0x110（D1）**YES** → 证明不是「唯一魔法地址」。

**真因**：`.rodata : ALIGN(16)` 结束紧贴 `.data` 起始（**仅差 12B**），新增任何代码/字符串
都平移整条段链，让缓冲地址**随机漂移进危险窗口**；叠加内核仅 4KB 上界余量 +
`.nvmedma : ALIGN(4096)` 一跨页就顶穿 `USER_BASE`（被空间守卫 fail fast 拦下）。
即「加功能必踩雷」是系统性地基问题，不是某个变量的锅。

**根治**：两个启动期 DMA 缓冲钉到固定物理页 `0x4007E000`（内核镜像前保留 RAM，
`fwc_ramfb_setup()` 在 `mmu_init()` 之前物理直访，QEMU DMA 直接读写 guest 物理内存，
开机仅一次）。`build.sh` 守卫重写为校验固定地址宏 + 保留区 + 间距/对齐 + 无残留静态符号，
正反通过；+2KB/+6KB 布局扰动下 ramfb 仍正常配置。段链再怎么浮动都不碰 DMA。

### 六、诚实的边界

- CPU 数字来自 QEMU TCG 沙箱，真机 KVM 绝对值不同，降幅方向一致；装机后用 `res` 复核。

  DEEP 档已压到 120Hz。

  余量不变。DMA 固定物理页解决的是「布局漂移导致开机挂死」，不是「空间不够」——
  后者按 [内核空间预算与扩容指引](内核空间预算与扩容指引.md) 第六节走。
- 桌面态抑制抢占期间 task1 心跳不打印，退出即恢复；串口 shell 路径完全不受影响。

## 第三十二轮（2026-11-11）：R 轮收尾勘误 —— 「串口假绿」与真实画面判据 ✅

### 一、全套回归打脸：8/11，三个图形测试全红

用第三十一轮的内核（fw_cfg DMA 缓冲钉在固定物理地址 `0x4007E000`）跑全套回归：
行为基线、NVMe/SCSI 装盘、UEFI 5 拓扑、EL0 33、P3 手感、资源在线验证全 PASS，
但 **P2 桌面 / P2.1 校准 / P2.2 鼠标跟随** 三个图形测试全 FAIL：

```
P2: 桌面完整渲染（颜色数>40） colors=2
    菜单区域差异=0.000  拖动窗口全屏差异=0.000
P2.2: 1/2/3 光标新框=0.000 旧框=0.000 -> 光标没动
P2.1: 校准层红色靶心像素=0  结果文字/靶心差异=0.000
```

手动 screendump 复核（进桌面后延时 0.2/1.2/3.2s）：**颜色数恒为 2、中心像素全黑**，
不是截屏时机问题，是画面根本没画出来。而串口 `[fb] fwcfg ramfb 已配置 800x600`
照常打印、CPU 在跑、wfi/tick/调频计数全对 —— 典型「静默假绿」。

### 二、铁证：用真实画面重做 A/B

| 缓冲方案 | screendump | 判定 |
| --- | --- | --- |
| 静态数组 `.data`（HEAD `0x400ae480`） | 800×600，97 色，中心 `(8,12,20)` | ✅ 真桌面 |
| 静态数组 `.data`（P3 前 `0x400b8778`） | 800×600 彩色 | ✅ 真桌面 |
| 固定地址 `0x4007E000`（< 0x40080000） | 640×480 纯黑 | ❌ surface 未建 |
| 固定地址 `0x400ae480 / 0x400ae520 / 0x4007F000` | 640×480 纯黑 | ❌ 同样黑屏 |
| **恢复静态数组（含全部 R1/R2/R3 改动）** | **800×600，97 色** | ✅ 正常 |

关键结论：**问题不在地址值，而在「把静态数组改成绝对地址宏」这件事本身**。
fw_cfg DMA 缓冲必须是内核镜像 **PROGBITS LOAD 段内的真实 RAM**：
`={1}` 让链接器写入初值、QEMU 加载器把该页纳入镜像；改成绝对地址宏后那块地址
不被任何 LOAD 段覆盖，descriptor 读出来无效 → QEMU 不建立 ramfb display surface
→ 回退 640×480 黑屏。`0x40000000-0x4007FFFF` 更是 QEMU loader/DTB 暂存区。

### 三、方法论根因（本轮最大教训）

第三十一轮的 7 组实验**全部用「串口出现 `图形桌面已就绪` / `fwcfg ramfb 已配置`」
当成功判据**——这两句是 `fwc_ramfb_setup()` 返回后无条件打印的，与 QEMU 是否真的
建了 surface 无关。于是「钉固定地址」被误判为可行并越走越远。密集扫描画出的
「危险窗口」是「挂死」判据下的现象，但**即使不挂死也可能是静默黑屏**。

**图形内核的成功判据必须是 screendump 真实像素，不能是串口日志。**

### 四、最终方案（磁盘真实版本）

1. **回退到静态数组**，不引入新段/宏：
   `static u8 fwc_cfg_buf[28] ... = {1};` / `fwc_dma_desc[16] ... = {1};`（PROGBITS `.data`）。
2. `build.sh` 守卫改为校验两符号**段类型 `d/D`** 且 `nm` 绝对地址 **≥ `0x40080000`**
   （镜像内已映射 RAM，禁止退回 `.bss` 或改绝对地址宏），并明确注释「禁止用进桌面当判据」。
3. 新增 **`test_framebuffer.py`**：每次回归直接对 screendump 做像素级判定
   —— 尺寸必须 `800×600`（surface 建成才是这尺寸，未建 QEMU 回退 640×480）、
   颜色数 >16、非背景占比 >1%。任一不满足即 FAIL 并打印「黑屏/未建 surface」。
4. 新增 `diag_res.py`：图形链路异常时读 guest 计数判定「wfi 真省电还是睡死」。
5. R1/R2/R3 主体（timer cycle 结算、自适应调频、`res` 命令、桌面 wfi）**全部保留**，
   与本勘误无冲突；CPU 50%→0.6%、`test_resource_live.py` ALL PASS 仍成立。

结论修正：`.rodata/.data` 浮动布局确实让缓冲地址随新增代码漂移，但**根治手段不是
钉地址，而是用真实画面判据在每次回归里守住**——加代码后画面仍出即 DMA 正常，
黑屏/HANG 立刻 fail fast。比「固定地址 + 一堆段/对齐约定」稳健得多。

## 第三十三轮（2026-11-11）：虚拟机优雅关机 / 重启 —— PSCI SYSTEM_OFF / SYSTEM_RESET + 桌面按钮 ✅

### 背景
用户在飞牛 KVM 虚拟机上点管理器的「关机」「重启」都无效，只能「强制关机」。

### 问题根因
- 本系统是自己写的 **EL1 内核**，用 QEMU `-kernel kernel.elf` 直启，**没有 ACPI 表、没有 guest-agent**。
- 虚拟机管理器的「关机 / 重启」本质是发 **ACPI 电源键事件**（或调用 guest-agent），内核根本收不到。
- 内核此前也**没有任何关机 / 重启代码路径**（只有 SMP 下的 PSCI `CPU_ON`），所以电源按钮等于石沉大海。

### 修法
- 从系统内**主动**用 PSCI 标准接口触发：
  - `SYSTEM_OFF   = 0x84000008`（优雅关机：QEMU 收下后停 vCPU，KVM 上即虚拟机关机）
  - `SYSTEM_RESET = 0x84000009`（重启：QEMU 重置 vCPU，KVM 上即虚拟机重启）
- `psci_call()` 先读 `ID_AA64PFR0_EL1` 探测 EL2 / EL3 是否存在，再选 conduit：
  - 有 EL2 先试 `hvc #0`（KVM / QEMU `virtualization=on` 走这条；TCG 下也经 EL2 陷入提供 PSCI）
  - 再试 `smc #0`（裸机 EL3 固件；QEMU 加 `virtualization=on` 时 SMC 也陷入 EL2 提供 PSCI）
  - 命中（`x0 == 0`）即返回；**无可用 conduit 时优雅返回 `-1`，绝不执行会 UNDEF 的 `hvc`/`smc`**
    （`-machine virt` 在 EL3/EL2 都缺时这两条指令是 UNDEFINED，直接崩）
- 新增 4 条等价命令：`poweroff` / `shutdown` / `halt`（三者均走 `SYSTEM_OFF`）+ `reboot`（`SYSTEM_RESET`），写进 `help`。
- 桌面「开始菜单」新增「关机」「重启」两个按钮（`ACT_EXEC` 执行同名命令，与手敲完全一致）。

### 连带：预算守卫越界 → 顺手落地《指引》方案 1（`.bss.align4k`）
- 加 PSCI + 命令后内核净增约 344 字节，把原本就只剩 **4 KB 下限**余量的内核顶过一页：
  `__nvmedma_end == USER_BASE(0x40210000)`，余量 0，`build.sh` 守卫 `rc=1` 拦截。
- 采用《内核空间预算与扩容指引》第六节 **方案 1（治本）**：把 `.bss` 里约 30 个 `aligned(4096)`
  缓冲（页表 / virtio 队列 / EL0 演示页等）统一收进独立段 `.bss.align4k`，置于小变量之后、栈之前。
- 效果：`align_gap_bytes` **2592 → 0**，余量回到 4 KB，构建通过且行为零变化。
  （`nvme.c` 的 `.nvmedma` 已是独立 4 KB 段、`.el0text` 等函数段刻意跳过，未误标记。）

### 验证
- **`test_power.py`（纯串口，`virtualization=on`）**：
  - `poweroff`：guest 干净断电（vCPU 停机，QEMU 进程 CPU 0%、线程 `State=S`）✓
  - `reboot`：进程存活且内核重新启动（开机横幅再现）✓ → **ALL PASS**
- **回归护栏（零回归）**：
  - `test_framebuffer.py` PASS（800×600 / 97 色 / 非背景 71.6%）
  - `test_resource_live.py` ALL PASS（tick 恒 10Hz、自适应降档、MMU 正常）
- **ISO 重建**：`build.sh` `rc=0`；五方 `kernel.elf` md5 一致（`a39b85248e2cf54597053183e30aeb65`）；
  `iso/自研内核ISO/loongos.iso` 已刷新，md5 `617366533bf3265ec21da142763d22b1`。

### 交付与注意
- ISO 在 `.gitignore`（`*.iso`）内，走 GitHub Release / NAS 分发，不进仓库；
  `kernel.elf` / `kernel.o` 按仓库既有策略保留并随源码同步提交。
